## 0. 一句话

**给每一次上线变更配一个不下班的评审员**：它读变更单、读代码 diff、读配置和 SQL 脚本，对照公司规范和历史故障，30 秒给出风险评级、影响面、检查清单、时窗建议和回退预案草稿，高危项直接拦下，人只做"放行 / 打回"的最后一步；每一次放行和每一次事故都回写进它的记忆，越用越准。

**为什么是它**（对照评委的五把尺子）
- 业务价值：期货公司的变更事故代价极高（交易时段一次故障 = 客户无法下单 + 监管报告）；变更评审目前靠人肉、靠老师傅，评审质量随人、随时间波动。
- 创新性：不是又一个"AI 写代码"，而是把 **变更单 + 代码 diff + 配置/SQL + 历史故障库 + 行业规范** 五路信息合到一次评审里，加期货特有的"交易时窗"规则和"变更—故障"数据飞轮。市面工具（CodeRabbit、CodeBuddy 评审）只看 diff、不懂变更流程和期货时窗。
- 技术落地：静态分析 + 规则引擎 + LLM 三层，全内网可跑，接入方式是 git hook / CI 插件 / 工单系统 webhook，不改现有流程。
- 可复制：任何系统、任何语言、任何子公司都要做变更，接入成本是"配一个仓库地址 + 一个工单字段"。
- 安全合规：直接对应行业标准 JR/T 0099—2012《证券期货业信息系统运维管理规范》第 6.3 节变更管理的每一条（见 §4），代码/配置进模型前先脱敏（复用研伴"隐盾"）。

## 1. 痛点故事："一个上线的晚上"

**现在**
- 18:30 收盘后，开发小李提交变更单："结算报表服务，优化保证金计算，附 SQL 脚本"。变更单里"回退方案"一栏写着"回滚代码"。
- 评审人老王手头还有三个变更单，粗看了一眼 diff，没注意到 `Decimal` 被改成了 `float`，也没注意到 SQL 脚本里有一条 `ALTER TABLE ... DROP COLUMN` 没有回退脚本。
- 21:00 夜盘开盘，报表金额出现分位误差；02:30 夜盘结束后回滚，发现列已删、数据要从备份恢复。
- 第二天写事故报告，查了两小时才把"改了什么 → 影响了谁 → 谁批的"串起来。

**用了守门员**
- 18:31 变更单一提交，守门员自动读 diff、SQL 和变更单，输出：**风险 L4（高）**。三条硬伤：① 金额精度 `Decimal→float`（结算相关，历史上 2024-xx 有同类事故，待校准）；② DDL 无回退脚本，已自动生成回退草稿；③ 计划实施时间 20:40 距夜盘开盘不足 30 分钟，建议改到 02:40 夜盘结束后或次日结算后。
- 老王只需看这三条，30 秒决定"打回"。小李按建议改完再提，守门员复评 L2，附上检查清单（测试证据、监控指标、通知对象），老王放行。
- 一切留痕：谁提、AI 说了什么、人怎么决定、实际结果如何 —— 事后审计一键导出。

> 痛点数字（方案文档需校准）：公司年变更次数 N、变更引发的事件占比 x%、平均评审耗时 t 分钟/单、评审人集中度（前 3 人承担 y%）。建议做内部小问卷 + 从工单系统抽样 3 个月。

## 2. 产品概念与包装

延续研伴的做法：一个有名字的"人" + 几项可复用的技能 + 一道安全门。

**候选名字**（Jerry 定）
1. **「门神」**（推荐）—— 变更过门神，上线不惊心。年节贴门神、上线过门神，一听就记住；技能全部用"门"的意象。
2. 「守门员」—— 足球意象，"最后一道防线"，中性稳妥。
3. 「安心上线」—— 直白，偏产品化，不像人名。

**技能（Skills，以「门神」命名为例）**

| 技能 | 做什么 | 输入 | 输出 |
|---|---|---|---|
| **读单** | 变更画像：改了什么、属于哪类（代码/配置/数据/基础设施）、涉及哪些模块、表、接口、外部依赖 | 变更单文本、git diff、SQL/配置文件 | 结构化变更卡片 |
| **审码** | AI CodeReview：规则引擎（高危模式）+ LLM（语义评审）双引擎，命中即给修改建议，L4 项可阻断 | diff + 公司编码规范 + 规则包 | 风险点列表（证据行号、级别、建议） |
| **探影** | 影响面与相似故障：依赖/调用关系推断受影响系统与下游（柜台、行情、风控、结算、报送），检索历史故障库找"同类变更曾出事" | 变更卡片 + 依赖图 + 故障库 | 影响面图 + 相似故障提示 |
| **定窗** | 时窗与预案：对照交易时段/夜盘/结算时间给出可实施窗口，生成检查清单和回退预案草稿（含 DDL 回退脚本） | 变更卡片 + 交易日历 + 规范条款 | 时窗建议、检查清单、回退草稿 |
| **留痕** | 台账与飞轮：AI 结论、人工决定、实施结果、事后关联故障，全部入库；月度"变更健康度"报表 | 全流程事件 | 审计台账、统计报表、飞轮数据 |
| **隐盾**（复用研伴） | 代码/配置/变更单进模型前脱敏：密钥、内网 IP、账号、客户字段；模型只见结构化摘要；本地规则兜底 | 任何进模型的文本 | 脱敏文本 + 脱敏日志 |

**规则包里放什么（期货 IT 特色，先列 12 条，Demo 至少实现 8 条）**
金额/数量精度用浮点｜DDL 无回退脚本｜删表删列｜大表无索引全量更新｜事务缺失或范围过大｜硬编码密钥/密码/内网地址｜日志打印客户敏感字段（证件号、手机号、资金账号）｜异常被吞（空 catch）｜时区/交易日历硬编码｜行情/柜台连接参数改动未走灰度｜计划实施时间落在交易时段或距开盘不足 30 分钟｜变更单缺"回退方案 / 测试方案 / 应急预案"字段。

**接入形态**（三种，Demo 做第一种，方案里讲三种）
1. 网页：粘贴 diff / 上传变更单 / 选一个 PR → 出报告（Demo 用）
2. git hook / CI 插件：Merge Request 上自动评论、打标签、阻断合并
3. 工单系统 webhook：变更单提交即触发，评审结论回填到变更单

## 3. Demo 设计（现场可跑、只用模拟数据）

**载体**：Streamlit 网页（沿用研伴技术栈：`llm.py`/`config.py`/`.env` OpenAI 兼容接入、`privacy.py`、SQLite 留痕、mock 模式无 key 可跑）。

**模拟对象**：一个虚构的"客户保证金监控与结算报表服务"仓库（Python + SQL，几百行，结构像真的：`settlement/`、`quote/`、`report/`、`db/migrations/`），配一份虚构的变更单模板和 8 条虚构历史故障。

**预置 6 个变更（一键选择，也可现场粘贴 diff）**

| # | 变更 | 预期评级 | 命中规则 |
|---|---|---|---|
| 1 | 结算金额 `Decimal → float` | L4 | 精度 + 相似故障 |
| 2 | 迁移脚本 `ALTER TABLE DROP COLUMN` 无回退 | L4 | DDL 无回退 → 自动生成回退草稿 |
| 3 | 行情源地址与超时参数改动，直接全量 | L3 | 连接参数未灰度 + 影响面（行情→风控→柜台） |
| 4 | 日志新增打印客户手机号 + 硬编码数据库密码 | L4 | 敏感字段 + 密钥 → 隐盾同时演示脱敏 |
| 5 | 页面文案与按钮颜色 | L1 | 无命中，检查清单最简 |
| 6 | 低危代码但计划 14:30 实施 | L3 | 时窗规则（JR/T 0099 6.3.5） |

**现场 3 分钟流程**：选变更 #1 → 30 秒出报告（评级、三条硬伤、影响面图、时窗建议、回退草稿）→ 点"打回"，填一句理由 → 切到变更 #5 放行 → 打开"留痕"页看台账与月度健康度 → 现场粘贴一段评委给的 diff（附加分：真实环境交互）。

**评测指标（方案文档里要有数）**：规则召回率（预置 30 个含缺陷 diff）、LLM 评审误报率、评级与人工评级一致率、单次评审耗时、脱敏漏检率。Demo 里带 `eval_review.py` 跑分。

## 4. 安全合规：直接对标行业标准

JR/T 0099—2012《证券期货业信息系统运维管理规范》第 6.3 节（变更管理）要求：建立变更流程（6.3.1）；明确申请人、审批人、实施人、复核人（6.3.2）；变更申请须含目标、对象、时间、人员、紧急程度、操作步骤、测试方案、实施方案、风险防控措施、应急预案、回退方案（6.3.3）；审批人须在充分评估技术风险和业务风险的基础上审批，记录满足审计要求（6.3.4）；除紧急变更外不得在交易时段实施（6.3.5）；变更前后测试、更新配置库、评估变更结果（6.3.6–6.3.8）。

守门员逐条对应：读单校验 6.3.3 的必填项 → 审码/探影替审批人做 6.3.4 的技术与业务风险评估 → 定窗执行 6.3.5 的时窗约束并生成回退方案 → 留痕满足 6.3.4 的审计记录与 6.3.8 的结果评估。方案 PPT 上用一张"条款 ↔ 技能"对照表讲安全合规页，评委一看就懂。
（条款文字来自公开标准文本摘录，方案文档定稿前按 PDF 原件核对措辞与编号。）

数据安全三道线：① 代码与配置不出内网，模型走公司 AI 平台 API；② 隐盾脱敏在前，模型只见摘要；③ 全程只读、不自动执行任何变更，人是最后一道门。

## 5. 五维打分（对着评委的尺子）

| 维度 | 权重 | 分 | 理由 |
|---|---|---|---|
| 业务价值与成效 | 25% | 4 | 变更事故代价高、痛点全公司技术条线共通；成效数字要靠内部数据校准（年变更量、事件占比、评审耗时） |
| 创新性 | 20% | 4 | 五路信息合审 + 期货时窗规则 + 变更—故障飞轮；比"AI 写代码"更贴管理场景，但"AI CodeReview"本身不新 |
| 技术与落地可行性 | 20% | 5 | 三层架构成熟、全内网、hook/CI/webhook 接入不改流程；Demo 可完全自建 |
| 可复制推广性 | 20% | 4 | 系统无关、语言无关、子公司通用；规则包需按各系统微调 |
| 安全与合规管控 | 15% | 5 | 逐条对标 JR/T 0099 变更管理条款；脱敏、只读、留痕 |
| **加权** | | **87** | 研伴 89。两者不冲突：研伴讲业务前台，门神讲技术后台 |

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 评委觉得"就是 AI CodeReview" | 开场用变更单 + 时窗 + 回退预案讲，CodeReview 只是六技能之一；对照表讲规范条款 |
| 拿不到真实代码与故障库 | Demo 全虚构，方案里写"接入公司 GitLab/工单只需配置"；成效数字用问卷 + 抽样 |
| LLM 误报惹开发反感 | 规则引擎做硬判、LLM 只做建议；误报可一键标记，进飞轮 |
| 现场网络/API 不可用 | mock 模式内置全部 6 个案例的离线结果 |
| 与研伴撞时间 | 复用同一骨架；先做规则引擎 + 6 案例（2 天），再接 LLM（1 天），最后做界面包装（1 天） |
