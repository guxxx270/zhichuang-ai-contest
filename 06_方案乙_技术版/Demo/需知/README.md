# 需知 · 需求分析智能体（Demo v0.5）

> 一堆话进来，一份能开工的需求出去。
> 团队赛方案乙（技术部视角）的 Demo。页面顶部两种用法：
> 1. **零散需求 → 完整需求**：微信三句话、一段会议纪要、一封邮件、一页 Word 扔进去，它先出一版需求，然后告诉你：要和业务确认哪几件事、这活多复杂、大概多少人天、哪几处要 IT 拍板，顺手把可点的原型页画出来。一段纪要里提了好几件事，「纪要直通车」识别出来，一键拆成几条分别受理。
> 2. **Jira 需求评估**：已经写好的 Jira 工单（粘贴一条，或上传 Jira 导出的 CSV / Excel 一次评一个迭代），给出技术复杂度、传统工时、**AI 编码工时**（编码阶段）与全流程 AI 协同工时，并和故事点 / 原始预估对比。
>
> 两种用法接得上：「写单」页一键「转成 Jira 工单去评估」。

## 启动

- **Windows**：双击 `启动需知.bat`（首次自动建虚拟环境并装依赖），浏览器打开即可。需要 **Python 3.10+**（推荐 3.12）。若 PATH 里的 `python` 是 3.7，脚本会改用 `py -3.12`。
- Mac：双击 `启动需知.command`（首次自动建虚拟环境并装依赖），浏览器打开即可。
- **企微入口**：双击 `启动企微入口.command`，之后在企业微信里 @需知 发需求即可（见下文「企微入口」）。
- **REST API / MCP**：双击 `启动接口.command` 起 REST（http://127.0.0.1:8770/docs）；`python mcp_server.py` 起 MCP（见下文「接口」）。
- 手动（Mac/Linux）：`pip install -r requirements.txt && streamlit run app.py`
- 手动（Windows PowerShell，在本目录执行）：

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
streamlit run app.py
```

- 命令行看全流程：`python run_demo.py 1`（1～6 为六个样例；⑥ 会先列出纪要里识别到的几条需求；请用上面虚拟环境里的 python）
- 测试：`pytest -q tests`

不配置 Key 可以整理需求、写单、出原型，并查看**规则模板与历史记录参考**。配置模型后增加独立的大模型估时；未配置或调用失败只影响模型结果，不影响其他参考。页面只展示真实模型；**开工先显示规则初稿，再后台调用已配置的模型增强**。规则与历史参考、需求单和原型无需等待模型返回；未填 Key 时保留这些快结果，不显示模型运行中的状态。**页面底稿 / Git 仓库**：可上传 HTML，或粘贴多个文件/整仓链接；整仓会浅克隆并抽取前后端源码摘要，模型据此问清、估时、定架、出样（复刻现页再改）。**口述**仍可用（注意厂商语音服务合规）。API Key 仅会话有效。运维可把公司 AI 平台（任意 OpenAI 兼容网关）写进本机 `.env` 的 `LLM_API_BASE` / `LLM_MODEL` / `LLM_API_KEY`：网关是预设之一就默认选它；不是预设时默认选「自定义网关」并带出网关地址、模型与 Key，打开页面即可用，页面上改了以页面为准。

估量中的“现在”按可检索仓库、修改代码、运行测试并迭代修复的编程代理场景比较；工具权限和开发环境属于待验证前提，会随结果保存并展示。两轨统计有效人时，无人值守运行和等待不计入；共享的定位、样本与核对工作不重复计时。未提供代码仍标为粗估，不等于实施时无法使用代码。模型逐项说明操作投入，不预设提效比例；规则模板与历史参考仍独立保留。

## 六项技能（v0.3：六项都有——对账落在「一本账」里）

| 技能 | 做什么 | 引擎 |
|---|---|---|
| **问清** | 抽需求卡片；按「期货 IT 需求追问知识库」+ 通用检查项生成**待确认清单**（影响高 / 中 / 低，附"不问会怎样"与默认假设）；一键生成给业务的确认消息；业务答复后重算 | 规则 + 模型润色 |
| **写单** | **双版需求单**：业务版一页纸（可签字）+ 技术版（用户故事、Given/When/Then 验收、数据字典、接口草案、非功能），技术条目回链原话 | 规则模板 + 模型润色 |
| **估量** | **先出参考，后台补模型结果**；**三方参考并列展示**：独立模型分析、规则模板参考、历史记录。模型按本条需求和已提供材料拆分工作，分别估「以前（人工开发）」「现在（AI协同）」的区间与参考值，附逐项理由和证据；无有效代码依据时标为粗估。规则参考展示自己的公式、任务与前提；历史记录列明当时估算、实际工时及开发方式。无 Key 仍能看规则与历史；三路不自动加权混合，仅有效模型数字进入模型工时汇总 | 模型分析 + 独立规则参考 + 历史检索 |
| **定架** | 技术栈建议、分层架构图、**复用发现**（对照公司系统目录）、**数据地图**（需求里的每个数据项定位到 系统 · 数据域 · 接口 · 时效，汇总可复用 / 需申请 / 需新建，盘中类需求自动查时效够不够）、**IT 决策清单**（选项 / 推荐 / 理由 / 影响）→ ADR（含数据地图）；有页面底稿时优先建议「在现页增量改」 | 规则 |
| **出样** | 可点的 HTML 原型：有底稿且调模型时，模型读 HTML 复刻布局再按需求改；失败则规则插列；无底稿用四套模板。手机版、客户版可切 | 模型读底稿 + 规则兜底 |
| **对账 · 一本账** | 需求从受理到交付全程一本账（受理 / 已确认 / 开发中 / 已交付 / 已对账）；交付后回写实际人天 → 写入 `data/history_learned.json`，作为后续复盘依据；**需求经营看板**（各部门需求量、类型、状态漏斗、平均追问与澄清轮次、有效模型估算预计省时、估算偏差）全部由台账实时算出；审计台账可导出 CSV；每条需求的**版本记录**任选两版对比、下载变更说明（见下文「需求版本对比」） | 纯程序计算 |
| 隐盾 | 原话、上传的 HTML 底稿、仓库代码摘录进模型前都先脱敏（手机、账号、证件、内网地址、密钥、客户 / 机构名 → 语义标签，模型输出再还原），本地规则；凭据类文件（.env、*.pem、*secret*）不读；**沙箱策略** `sandbox.yaml` 一页写清所有访问边界并标出代码执行位置；**模型调用审计**每次调用落一行 | 规则 |

估时原则：**模型、规则模板、历史记录各自说明依据，供人工比较，不自动加权混合**。模型独立拆工作并分别估算以前与现在，程序校验和汇总模型逐项数字；规则公式单列为参考，不用来补写模型结果。历史实际工时可能对应不同范围与开发条件，不直接套入本次需求。各处按 8 小时 = 1 人天换算，表示投入工时，不是日历工期；只有成功的模型估时进入模型工时汇总。

## Jira 需求评估（v0.5）

| 步骤 | 做什么 |
|---|---|
| 读工单 | 粘贴：认单号、摘要、类型、优先级、模块、故事点、原始 / 剩余预估、实际耗时，以及描述里的「验收标准 / 技术说明 / 复现步骤 / 期望结果」段；导出：认 Jira 中英文表头，时间列按秒，同名「模块」列合并，Σ 汇总列忽略；人名字段不读 |
| 技术六维 | 改动规模、涉及系统、数据与口径、接口与性能、测试与验收、风险与依赖，每维 1～5 分并引用工单原文作依据（「不改表结构」「结算系统」这类不误判） |
| 工时 | 类型基线（缺陷 / 任务 / 需求 / 改造）+ 六维加权 → 规则模型；用已完成工单的实际耗时算团队系数，并只和**同类型**已完成工单类比（缺陷不拿需求比，史诗不类比） |
| AI 编码工时 | 主数只算编码阶段：编码实现、单元测试、自测联调、代码评审（缺陷另含定位排查），逐项乘 AI 系数；交易链路上的编码只按「AI 做人审」折算。全流程（设计 / 测试 / 上线）另列 |
| 质量检查 | 代替追问：缺验收标准、验收太少、缺陷没写复现 / 期望、没写影响范围、触及交易链路、涉及客户数据、提了性能没给指标、提到夜盘 / 节假日但验收里没场景、史诗该拆 |
| 对比原估 | 有原始预估就直接比；只有故事点就按已完成工单折算「1 点 ≈ x 人天」再比，偏差 ≥ 40% 标出来 |
| 记进一本账 | 每条评估记一行（来源 Jira，单号去重：再评只更新并记「Jira 重新评估」）；状态随 Jira（待办 → 已确认、进行中 → 开发中）；Jira 里已完成且有耗费时间的直接按实际对账。对过账的 Jira 工单成为下次评估的校准样本（Jira 自己的飞轮，不写零散需求的历史库）。看板的部门 / 类型分布与追问、澄清指标只算零散需求，Jira 单独汇总编码阶段人工 → AI；「写单」页转过来的评估挂回原来那行账 |

校准样本：把公司 Jira 导出的历史工单（含耗费时间）放进 `data/jira/历史/`，估算即按团队实际耗时校准；没有时用 `data/jira/示例_迭代导出（虚构）.csv` 里已完成的 8 条（虚构）。代码：`xuzhi/jira.py`（解析）、`xuzhi/pipeline/assess.py`（评估）、`app_jira.py`（页面）。

## 纪要直通车（一段纪要拆成几条需求）

晨会、周会纪要里常常一口气提好几件事：研究所要周报、风控部要提醒、资管部要页面。整段当一条需求分析，问题、工时、原型都会混在一起。开工后如果识别到 2 条以上需求，结果页签上方出现「纪要直通车：这段话里识别到 N 条需求」，列出每条的提出方、预览和拆分依据；点「拆成 N 条分别受理」，每条单独走问清、写单、估量、定架、出样，在一本账里各记一行。单条需求不出现任何提示，原来的流程不变。

| 规则 | 说明 |
|---|---|
| 怎么切 | 按优先级：行首编号条目（1. / 1、 / （1） / 一、 / ① / - •）→ 部门开头（「风控部提出：」「研究所：」「资管部希望」）→ 句首连接词（还有一件事 / 第二件事 / 另外 / 此外 / 再就是 / 顺便）。编号只在像纪要、开头说了「几件事」或至少两条编号各带提出方时才切：需求单里的 1. 2. 3. 是同一条需求的功能点；「要求如下：」「需求如下：」后面的编号、低一级或缩进更深的编号（1. 下面的 - / （1））、紧跟在「谁要做什么」那句后面的列表都算这一条的要点；「营业部补充：」接着上一条说，「营业部补充一个需求：」才另起一条 |
| 什么算一条 | 有需求动词（要 / 希望 / 能不能 / 自动 / 提醒…）、不少于 12 字；参会名单、背景、「下周再议」这类决议、领导表态不算（「能不能做个…，具体字段下周再议」仍算一条）；太短的、只是上一条要点的并回上一条；单次最多 8 条 |
| 带上什么 | 头部元信息（来源 / 时间 / 记录 / 主题 / 标题 / 日期）每条都带上，来源识别照常；参会名单不带（名单里的部门会被认成提出方）。头部点名的部门和本条提出方不同时，本条首行写明「提出方：××」 |
| 提出方 | 本条开头点名的部门；没点名的沿用小节标题、开场白（「风控部提出两件事：」）或头部；段内别处出现的部门多是收件人，排在最后。开头点了领域词典里没有的部门（「结算部需要…」）照原话显示，不借上一条或头部的提出方；这类部门需求分析暂认不出，一本账里记「未注明」（头部点了部门时记头部的） |
| 记账 | 每条记一行，流水「纪要拆分受理 · 同一段纪要拆出 3 条，第 2 条（原纪要 #12）」；整段那行保留原文，流水记「纪要拆分 · 已拆分为 #13 #14 #15」，台账明细与对账下拉里标「整段纪要，已拆为 #13 #14 #15」。看板、首页「已分析需求」和催办摘要不再把整段那行算成一条（按拆出的 3 条算）；这一标记存在一本账的 `split_into` 列，老库打开时自动补列，`GET /api/v1/requirements` 与导出的 CSV 里也有 |
| 切换查看 | 拆完显示各条的编号、标题、类型、待确认数与规则参考（以前 → 现在，小时），用「查看哪一条」切到任意一条或回到整段，下方各页签跟着换；答复重算记在各自那行；填了还没点重算的答复按条留着，切走再回来接着填。拆分本身和每条受理都只用规则，要模型润色可在切过去的那一条里点 |

接口同样能用：`POST /api/v1/split`、MCP `xuzhi_split`（见下文「接口」）。代码：`xuzhi/pipeline/split.py`（切分规则）、`xuzhi/service.py`（`split` / `run_split`）、`app_minutes.py`（页面）。

## 需求版本对比

需求会变：业务补一句话、答复改口径、模型补完估时，同一条需求的分析都会变样。需知把每次变化存成一版，说清改了什么、要找谁重新确认。

| 什么时候存一版 | 记为 |
|---|---|
| 开工受理 | 受理（v1） |
| 「问清」填业务答复后点重算（企微里按编号答复、接口带 `answers` + `req_id` 同理） | 业务答复重算 |
| 后台模型增强完成 | 模型增强 |
| 「估量」单独重新估时成功（失败不记） | 模型估时 |
| 原话改了：打开开工按钮下的「作为当前需求 #N 的新版本（需求变更）」再开工；接口带同一 `req_id` 发来改过的原话 | 需求变更 |

和上一版内容完全一样时不另存。两版之间比这些：

| 看什么 | 怎么比 |
|---|---|
| 功能点 | 新增 / 删除 / 改写（说法相近算改写，不算一删一增） |
| 要素 | 标题、类型、提出方、一句话理解、指标、品种、数据来源、渠道、期望时间、非功能 |
| 待确认 | 新增 / 不再需要 / 新答复 / 改答 / 说法变了（问法、影响档或默认假设） |
| 工时 | 模型估时只和模型估时比，规则参考只和规则参考比，两路数字不互相加减；有一版没有有效模型结果时只并列、不算增减 |
| 数据地图 | 按数据项比：新增 / 删除 / 来源系统、接口、时效、状态的变化 |
| IT 决策 | 建议变了 / 新增 / 删除 |
| **需重新确认** | 找业务：新冒出的高影响未答问题、问法变了的已答问题、原话改后不见了的功能点；找 IT 拍板：建议变了或新增的决策；找数据负责团队：新落到需申请 / 改动受控 / 需新建 / 时效不符的数据项（按状态归组）。原话没改、或一版是规则初稿一版含模型结果时，功能点增删只是说法差别，照常列出但不找业务确认 |

- **页面**：需求变更开关默认关；打开后开工沿用编号，仍在新清单里的题自动带上答复框里的口径（含刚填、还没点重算的），一本账同一行更新（受理时间、来源、提出方、状态不变）并记「需求变更」流水，开关随即复位（改选样例也复位），页面直接滚到「本次变更」。存了新版、且屏上正是这一版时，结果顶上出一行「本次变更」：一句话概要，展开看明细、下载本次变更说明；屏上结果和最新一版对不上时（如单独重估正在跑或刚失败）先不出，免得和估量页矛盾。
- **配了模型时**：答复重算、需求变更先存一版规则初稿，后台模型补全后再存「模型增强」。「本次变更」和上一份同类结果比（规则初稿比规则初稿、模型结果比模型结果），并注明跳过了哪几版，免得把「模型改写 ↔ 规则抽取」的说法差别当成需求变更；中间版本照样留在版本记录里。
- **一本账**：选中的需求下有「版本记录（N 版）」：每版是规则初稿还是含模型结果、功能点数、待确认（已答）、模型与规则工时；任选两版对比（默认最近两版；隔类相比时注明功能点差别多是说法不同），「下载变更说明 .md」直接发给业务和开发——先列需重新确认（可勾选），再分节写增删改。
- **存什么**：只存分析结果的紧凑快照、原话指纹（去空白后的哈希，只用来判断原话改没改）和引擎（规则初稿 / 含模型结果，只用来挑可比的版本），不存原话；与一本账同库（`versions` 表，老库打开时自动补表），不影响看板数字。Jira 工单走自己的「Jira 重新评估」，不记版本。
- 代码：`xuzhi/versions.py`（快照、对比、变更说明）、`app_versions.py`（页面）；接口见下文「接口」。

## 现场演示（上台前 5 分钟）

1. 先关掉需知，双击 `重置演示数据.command`（Windows：`重置演示数据.bat`）：一本账恢复成预置状态——20 条虚构需求、10 个部门、各状态都有、7 条已对账，催办摘要与追问记忆也有内容；答过题的预置需求各有两版，可在「版本记录」里对比。当前数据先整份备份到 `data/backup/<时间>/`。
2. 双击 `启动需知.command`，Chrome / Edge 全屏（1920×1080），首屏就是样例、原话与「需知，开工」；选模型、填 Key、底稿与仓库都收在「模型与参考材料（可选）」折叠栏里。
3. 建议顺序：样例 ① 开工 → 问清前两题（结算时点、比较基准）答「结算后为准，夜盘算下一交易日」「上一交易日结算价，不复权」→ 重算（结果顶上出「本次变更 · 已答 +2」）→ 写单 / 估量 / 定架 / 出样（出样切客户版，集中度列消失）→ 一本账看板 → 选样例 ⑤ 开工，回到「问清」看 🧠 沿用上次口径 2 条。
   需求变更（可接在重算之后）：原话末尾加一句「另外再加一列累计净值，盘中也要能看。」，打开开工按钮下的「作为当前需求 #N 的新版本（需求变更）」再开工 → 同一编号出 v3，「本次变更」列出需重新确认 3 项（新增高影响问题、D2 数据来源改为实时、6 个数据项时效不符），规则参考 80.8→150.4 小时；「一本账 → 版本记录」任选两版对比、下载变更说明。
4. 纪要直通车：选样例 ⑥（投研晨会纪要）开工 → 结果上方提示识别到 3 条需求（研究所 / 风控部 / 资管部）→「拆成 3 条分别受理」→ 在「查看哪一条」切到第 2 条，问清 / 估量 / 出样都换成风控部的追保提醒 → 一本账里多出 3 行，整段那行标着「整段纪要，已拆为 #…」、流水写着拆到了哪几条，看板按 3 条需求算。
5. Jira 评估：顶部切到「Jira 需求评估」→「上传导出（批量）」→「用示例导出（虚构 14 条）」，看汇总、柱状图与逐条表；点 XZ-1040 看「原估偏乐观」，点 XZ-1036 看交易链路风险。也可在「零散需求」写单页点「转成 Jira 工单去评估」。
6. 开工后先查看需求初稿、规则与历史参考、需求单和原型；配置了模型时，后台继续增强，页面显示当前步骤、已用时间及运行状态，完成后自动刷新同一条需求。也可在估量页点「大模型分析估时」或「重新分析估时」单独后台估时；运行中不能重复启动同一操作，但可以开新需求，旧任务随后完成也不会覆盖新需求。
7. 未填 Key 时不显示模型加载状态；“尚无模型结果”表示还没有有效结果，不表示正在调用。模型失败或返回不合格时显示失败原因，规则、历史和已有需求初稿仍可使用。模型单次调用上限 `LLM_TIMEOUT`（默认 90 秒）。

预置数据全部虚构：看板数字只用来展示界面，不是试运行成绩。预置不写模型调用审计（那张表只记真实调用，现场点一次润色就会出现）。

## 企微入口（需求直接从企业微信进来）

同事不用打开网页：在企业微信里 **@需知** 把一堆话发过去，需知当场跑完「隐盾 → 问清 → 写单 → 估量 → 定架」，
把**要和业务确认什么 / 大概多少人天 / 哪几处要 IT 拍板**回到聊天里；问题可以直接在聊天里回答，它按答复重算。

- **启动**：Mac 双击 `启动企微入口.command`；手动 `python -m xuzhi.channels.wecom.app`
- **配置**：`.env` 里填 `WECOM_BOT_ID` / `WECOM_BOT_SECRET` / `WECOM_ALLOW_USERS`（说明见 `.env.example`）
- **机器人怎么建**：企微管理后台 → 安全与管理 → 管理工具 → 智能机器人 → 手动创建 → **API 模式** → 连接方式选「**使用长连接**」。
  长连接由本机主动连出去，**内网不需要公网回调地址**，也不用做消息加解密。Secret 只显示一次，丢了在机器人详情页重新生成。
- **依赖**：企微入口用 `requirements-wecom.txt`（比 Web 端多 `websockets` 与 `claude-agent-sdk`），启动脚本会自动装

**聊天里有两种用法：**

**① 需求分析**（默认模式）
  - 发一段需求 → 回需求卡 + 要确认的问题（带编号）+ 模型双轨工时或待估算状态 + IT 决策点
  - 回「`1 按合约`」这样的编号行（可多行）→ 按答复重算，把握度和工时跟着变

**② 问码**：问关于需知这个项目本身的问题，它去翻代码回答（Claude Agent SDK，只读）
  - 单条：`/问 隐盾的脱敏规则在哪实现的` / `/问 加一个导出 PDF 要改哪几个文件`
  - 连着问：`/模式 问码` 切过去，之后直接发问题；`/模式 需求` 切回来；`/模式` 看当前
  - 回答带「依据」，每条指到 `文件:行号`；追问会续上同一个会话，不用重新交代背景
  - 只读锁死：只放行 Read/Grep/Glob，Bash/Write/Edit/Web* 从模型视野整体移除，`cwd` 锁在 Demo 目录，
    不加载本机 `~/.claude` 配置，另有轮数与墙钟双上限
  - 走 Anthropic 格式接口（`ANTHROPIC_BASE_URL` / `ANTHROPIC_API_KEY`），和需求分析用的 OpenAI 兼容口是两套；
    同一个中转站通常两套都能服务

**命令**：`/help` 用法 ｜ `/模式` 看或切模式 ｜ `/whoami` 查自己的 userid（配白名单用）｜ `/reset` 换一个需求 ｜ `/ping` 存活检查 ｜ `/摘要` 一本账催办摘要 ｜ `/记忆` 追问记忆统计（`/记忆 清 <提出方>`、`/记忆 清空`）

企微进来的需求同样进一本账（事件「企微受理」）；聊天里按编号答复后口径进追问记忆，下次同一提出方不再问，一本账也为这次答复存一版（可在 Web 端版本记录里对比）。

**对着评分表看**：需求本来就产生在聊天里，把入口放到企微等于零学习成本地接进现有工作流（可复制推广性）；
答问在同一个会话里闭环，现场能做真实环境交互演示（附加分）；进模型前先过隐盾、只放行白名单用户、
回复里不回显明文敏感信息（安全与合规）。

**边界**（企微官方限制，已在代码里兜住）：同一机器人同一时间只允许一条长连接，新连接会踢掉旧的；
最多 3 个并发交互；流式回复最长 6 分钟、单条 20480 字节 —— 所以聊天里只给当场要用的结论，
完整需求单 / 可点原型 / 数据地图仍在 Web 端。群聊只支持文本与图文混排。

## 接口（REST API / MCP）：任何入口都能接

**REST**：`python api.py`（或双击 `启动接口.command`），文档在 http://127.0.0.1:8770/docs 。
- `POST /api/v1/analyze` `{text, source?, answers?, req_id?, polish?, include_spec?, include_prototype?}` → 整条链 JSON（卡片、清单、确认消息、双轨估算、数据地图与决策、需求单）；答复重算时带 `answers` + 上次的 `req_id`，一本账在同一条上更新并写追问记忆
- `POST /api/v1/split` `{text, record?}` 纪要直通车：返回 `{count, segments:[{index, requester, reason, title_hint, body, text}]}`（片段已过隐盾）；`count` 为 0 表示只有一条需求，照常调 analyze；`record: true` 时逐条按规则受理、各记一行账，另返回 `results`（每条的紧凑结果，含各自 `req_id`），之后可带 `req_id` 答复重算
- `POST /api/v1/clarify` 只要问清；`GET /api/v1/requirements[/{id}]`、`POST …/{id}/status`、`POST …/{id}/reconcile` 一本账；`GET /api/v1/dashboard` 看板（含记忆与审计统计）；`GET /api/v1/digest` 催办摘要；`GET /api/v1/audit/llm` 模型调用审计；`GET /api/v1/sandbox` 沙箱策略
- 版本对比：`GET /api/v1/requirements/{id}/versions` 历次版本（版本号、时间、动作、快照）；`GET /api/v1/requirements/{id}/diff?from=&to=` 两版差异（默认最近两版；只给 `to` 时比它的上一版）→ `summary` 一句话、`diff` 结构化差异与需重新确认项（`diff.mixed` = 一版规则初稿一版含模型结果）、`markdown` 变更说明；版本不够或版本号不对返回 422。需求变更：带同一 `req_id` 发来改过的原话，按原话指纹识别，整条更新并记「需求变更」一版
- 安全：默认只监听 127.0.0.1；对外必须设 `XUZHI_API_HOST` 且配 `XUZHI_API_TOKEN`（否则拒绝启动）；请求体不接受模型 Key，模型只用服务端 .env；`polish` 默认 false（需求初稿走规则；估时以返回的状态为准，无模型时仍返回独立规则与历史参考）

**MCP**：`python mcp_server.py`（stdio）或 `--transport streamable-http --port 8771`（只听本机）。工具：`xuzhi_clarify` 问清 · `xuzhi_estimate` 双轨估算 · `xuzhi_architect` 数据地图与决策 · `xuzhi_spec` 需求单 · `xuzhi_analyze` 整条链 · `xuzhi_split` 纪要直通车（`record=true` 逐条受理）· `xuzhi_ledger` 一本账 · `xuzhi_reconcile` 对账 · `xuzhi_diff(req_id, from_version=0, to_version=0)` 版本对比（默认最近两版，返回差异、需重新确认项与变更说明）；资源 `xuzhi://sandbox`、`xuzhi://info`。
Claude Code：`claude mcp add xuzhi -- python /path/to/需知/mcp_server.py`；Cursor / Claude Desktop 的 `mcpServers` 里填同样的命令。三个工具带同一个 `req_id` 时落在同一条账上。

依赖：`pip install -r requirements-api.txt`（比 Web 端多 fastapi / uvicorn / mcp / httpx）。

## 催办摘要（附加功能，默认不推送）

一本账里"该动一动"的需求：待业务确认超 3 天、已交付超 5 天未对账、本周各部门受理数。**只有数量、需求标题、等待天数**，不含原话与客户信息。
- 拉取：企微发 `/摘要`；Web 一本账页「催办摘要」；`python -m xuzhi.reminders --print`；`GET /api/v1/digest`
- 推送（默认关）：要同时满足 `sandbox.yaml` `notify.enabled: true`、.env `XUZHI_DIGEST_WEBHOOK=企微群机器人 webhook`；再配 `XUZHI_DIGEST_TIME=09:00` 则企微入口进程每日定时推，或用系统 cron 跑 `python -m xuzhi.reminders --send`
- 阈值天数在 `sandbox.yaml` notify 段改

## 怎么换成公司真实资料

最省事的路：直接改 `tools/templates/需知_知识库_样本数据.xlsx`（Demo 现用的 30 条历史需求 / 36 条追问规则 / 13 个系统（含数据域与接口）已经在里面，替换成真实的即可），或从空白模板 `需知_知识库填写模板.xlsx` 填起（三个 sheet：历史需求 / 追问规则 / 系统目录，黄色区域填、第 3 行是示例），然后
`python tools/import_knowledge.py template 填好的模板.xlsx`（先加 `--dry-run` 预览）。有工单系统导出的话直接 `python tools/import_knowledge.py tickets 导出.xlsx`，列名按常见叫法自动识别、关键词自动抽取、小时自动折算人天，没有实际工时的记录会被跳过。写入前原 JSON 自动备份为 `.bak`。

手工改也行：

1. `knowledge/futures_probes.json`：加 / 改追问规则（触发词正则 → 问题 → 不问会怎样 → 默认假设 → 影响档）。
2. `knowledge/system_catalog.json`：换成公司真实系统目录（能力关键词、负责团队、接入方式；可选 `data_domains` 数据域与 `interfaces` 接口，填了「定架」就有数据地图；xlsx 模板的 G、H 两列对应）。
3. `data/history_requirements.json`：导入工单系统的历史需求与实际工时（含 `ai_assisted / ai_share`），用于复盘和后续校准；不按历史项目总工时直接套用到当前需求。
4. 估量页对照模型工作项与代码证据、规则模板公式和历史实际记录；分别核对适用范围与前提。修改模板只改变规则参考，不覆盖或预设模型分析结果。
5. `xuzhi/textutil.py`：品种、部门、渠道、数据源词典。

## 评测（成绩单怎么来的）

`python tools/eval_req.py` 把 `data/eval/eval_set.json`（20 条虚构需求，覆盖资管运营 / 资管 / 研究 / 投资 / 风控 / 合规 / 营业部 / 产业服务 / 财务 / 人力 / 技术部 11 类提出方与报表 / 页面 / 提醒 / 接口 / 数据 / 流程 6 类需求，每条配专家期望）跑一遍规则引擎，对照打分：类型识别、标题、数据来源、指标 / 品种抽取、追问覆盖率与误问率、IT 决策覆盖率、时效判断、脱敏漏检、数据地图定位率，成绩单写到 `data/eval/eval_report.md`。`tests/test_eval.py` 把规则分析阈值挂进测试，改规则退化会红。模型估时另外检查响应结构、证据范围、工时汇总和无模型/失败状态；不要求随机模型输出命中旧规则的固定区间。**换成公司真实需求（脱敏后）就是真实成绩单**：按同一格式填 `cases`，`python tools/eval_req.py 我的评测集.json`。

## 数据与合规

所有样例、历史需求、系统目录、原型数据均为虚构。**所有访问边界写在 `sandbox.yaml`**（隐盾页原样展示并标执行位置）。原话与材料（HTML 底稿、仓库代码摘录）进模型前都经隐盾脱敏，每次模型调用记审计（用途 / 网关主机 / 模型 / 耗时 / 出站脱敏标签数 / 明文敏感项数）；不接生产数据库；Git 仓库只在你主动填链接时浅克隆，只放行 http(s)、拒绝本机 / 内网地址，Token 走环境变量不进命令行与 .git/config，凭据类文件不读；原型预览在独立源的沙箱 iframe 里渲染，页面脚本读不到需知本页；每次分析、答复、状态、对账写入 `data/ledger.sqlite3`（追问记忆、模型调用审计、版本快照同库；`XUZHI_LEDGER_DB` 可改位置），对账回写到 `data/history_learned.json`（均已 gitignore）。
