## 0 一页看懂

## 1 产品简介与适用场景

### 1.1 一句话

**一堆话进来，一份能开工的需求出去。** 需知（XuZhi）是技术部与业务部门之间的「需求受理入口」：把零散的话问清口径、写成需求单，给出工时依据、数据来源和待拍板事项，全程记在一本账上。

### 1.2 两种用法

| 用法 | 输入 | 输出 | 何时用 |
|---|---|---|---|
| 零散需求 → 完整需求 | 微信三句话、会议纪要、邮件、Word 段落、口述 | 问清 / 写单 / 估量 / 定架 / 出样 / 对账，进模型前过隐盾 | 需求刚提出，口径未定 |
| Jira 需求评估 | 一条 Jira 工单，或 Jira 导出的 CSV / Excel | 技术六维、传统工时、AI 编码工时、全流程 AI 协同工时、与原估对比、质量检查 | 工单已写好，要排期或复核估算 |

两者接得上：「写单」页一键「转成 Jira 工单去评估」。零散需求一侧有七个页签（问清、写单、估量、定架、出样、一本账、隐盾），见 3.3。

「图：F02_six_steps」需求分析六步法：问清 → 写单 → 估量 → 定架 → 出样 → 对账，隐盾（进模型前本地脱敏）贯穿全程。

### 1.3 规则与模型怎么分工

- **规则出初稿与参考**：清单、需求单、规则模板工时、历史对照、数据地图、决策、原型，毫秒级、可复现。
- **模型做理解与估时**：改写标题与目标、补追问、润色需求单、拆工作项分别估「以前（人工开发）」与「现在（AI 协同）」、按底稿改原型。企微里只跑问清润色与估时两步。
- **程序校验与汇总**：模型逐项数字必须带证据，且能在原话、答复或代码摘录里逐字找到，通过校验才汇总；格式不合格时带着校验错误重问一次，仍不合格就不显示数字；模型自报的总数、系数、节省比例不采用。
- **三路依据并列，不混算**：模型、规则模板、历史记录不自动加权；只有成功的模型估时进入模型工时汇总和看板「预计省时」。

### 1.4 适用场景与边界

使用者：技术部受理人（出清单与需求单）、业务提出人（只答不同意默认的几条）、部门负责人（看工时依据、拍板项、看板）、开发（拿需求单、ADR、原型开工）。

边界：不接生产数据库、不改现有系统；数据地图来自系统目录（Demo 为虚构，需换成公司真实目录）；工时是投入工时（8 小时 = 1 人天），不是日历工期，也不是交付承诺；规则模板权重与 AI 系数为示例值，未用公司实际工时校准；对账只追加历史记录参考，不自动校准模型或规则模板（Jira 评估另按已完成工单算团队系数，见 5.6）。

## 2 快速开始

### 2.1 环境要求

| 项 | 要求 |
|---|---|
| 操作系统 | Windows 10/11 或 macOS（Linux 可手动安装） |
| Python | 3.10 及以上，推荐 3.12。开发环境为 macOS + Python 3.12.7【待团队填写：Windows 实机验证情况】 |
| 浏览器 | Chrome / Edge（口述只支持这两种） |
| 网络 | 首次安装依赖需访问 pip 源；调用模型需能访问所选网关；其余功能离线可用 |
| Git | 仅「Git 仓库」材料需要；带 Token 拉私有仓需 git ≥ 2.31 |
| 端口 | Web 8501（Streamlit 默认，只监听 127.0.0.1）、REST 8770、MCP HTTP 8771（默认也只听本机） |
| 数据库 | 无需安装，首次运行自动建本机 SQLite |

### 2.2 一键启动

| 系统 | 操作 | 脚本做了什么 |
|---|---|---|
| Windows | 双击 `启动需知.bat` | 依次找 `py -3.12`、`py -3.10`、PATH 里 ≥ 3.10 的 `python`、本机 Python312 安装目录；首次建 `.venv` 并装 `requirements.txt`，旧 `.venv` 版本过低会重建；然后启动页面 |
| macOS | 双击 `启动需知.command` | 用 PATH 里的 `python3` 建 `.venv`，每次启动补装依赖，日志写 `data/logs/启动_最近一次.log` |

浏览器打开 `http://127.0.0.1:8501`（端口被占用时会顺延，以终端显示的地址为准）。页面只在本机监听（`.streamlit/config.toml` 的 `server.address`），没有登录；要给局域网同事用，先放到带鉴权的反向代理后面再改。关窗口或 Ctrl+C 停止。

### 2.3 手动安装

```bash
# macOS / Linux，在需知目录执行
python3 -m venv .venv
./.venv/bin/pip install -r requirements.txt
./.venv/bin/streamlit run app.py
```

```powershell
# Windows PowerShell，在需知目录执行
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
streamlit run app.py
```

依赖分三份：`requirements.txt`（Web 端：pandas、streamlit、python-dotenv、openai、pytest、openpyxl、pyyaml；Streamlit 限定 ≥ 1.50、< 1.67，1.63～1.66 已跑通全部测试与出样预览，升级前先跑 pytest）；`requirements-api.txt`（REST + MCP，另加 fastapi、uvicorn、mcp 1.x、httpx）；`requirements-wecom.txt`（企微入口，另加 websockets、claude-agent-sdk）。

### 2.4 首次运行检查

1. 首页选样例「01_微信_资管运营_净值日报加列」，点「需知，开工」。
2. 下方出现七个页签；无 Key 时「问清」应有 12 条待确认（8 条高影响），期货题带 🌾。
3. 「估量」三张卡：独立模型估时显示「尚未调用模型」，规则模板（以前 65～145 小时）与历史记录（3 条）有数——这是无 Key 时的正常状态。
4. 命令行自检（用虚拟环境里的 python）：

```bash
./.venv/bin/python run_demo.py 1        # 1～6 为六个样例，打印问清 / 写单 / 估量 / 定架 / 出样；6 会先列出纪要里识别到的几条需求
./.venv/bin/python -m pytest -q tests   # 自动化测试：39 个测试文件、548 项，全部通过
```

Mac 另有 `检查接入.command`：检查 `.env` 里的模型网关能否连通，连通后用样例 1 跑一遍，日志写 `data/logs/检查接入_最近一次.log`。

### 2.5 演示数据重置

上台前先关掉需知，双击 `重置演示数据.command`（Windows：`重置演示数据.bat`，需先运行过一次 `启动需知.bat`），完成后再打开需知（旧页面里的需求编号已失效）。等价命令：

```bash
./.venv/bin/python tools/demo_seed.py           # 备份 → 清空 → 预置
./.venv/bin/python tools/demo_seed.py --empty   # 备份 → 清空，一本账从 0 开始
```

| 步骤 | 内容 |
|---|---|
| 备份 | `data/ledger.sqlite3` 与 `data/history_learned.json` 整份复制到一本账旁边的 `backup/<时间>/`（默认 `data/backup/`） |
| 清空 | 需求、流水、反馈、追问记忆、模型调用审计、版本六张表；删除 `history_learned.json` |
| 预置 | 用规则引擎真实跑 20 条虚构需求：10 个部门，受理 5 / 已确认 3 / 开发中 3 / 已交付 2 / 已对账 7；按业务答复重算过的各有两版；追问记忆、催办摘要有内容 |
| 刻意不做 | 不写模型调用审计（只记真实调用）；不生成模型工时；不预置资管运营的记忆，保证样例①开工是全新一条 |

预置数字只用于展示界面，不是试运行成绩。看板上「规则模板参考 vs 实际」一行（平均偏差 29%，7 条已对账）同样来自虚构数据，且模板权重未校准。

### 2.6 上台前 5 分钟

1. 重置演示数据 → 双击启动 → Chrome / Edge 全屏（录屏 1920×1080）。首屏就是样例、原话与「需知，开工」；选模型、填 Key、底稿与仓库都收在「模型与参考材料（可选）」折叠栏里，投屏不露出。
2. 演示顺序：
   1. **样例①**开工 → 问清前三题答「结算后为准，夜盘算下一交易日」「上一交易日结算价，不复权」「客户版去掉集中度」→ 重算：提示「已按 3 条答复重算」，结果顶上出「本次变更」，概要含「已答 +3」（只用规则时为「v2 · 业务答复重算　相对 v1：已答 +3」；配了模型时编号顺延，见 4.3），可下载变更说明。
   2. 写单 / 估量 / 定架 / 出样：估量页规则模板参考从「以前 65～145 小时（参考 81）/ 现在 40～90 小时（参考 50）」收窄到「以前 65～133 / 现在 40～83」（答了 3 道高影响题），标「未校准」，附六维雷达、分维工时与按分工给的交付建议；出样切客户版，表格里的集中度列消失（模型生成的页面里「集中度预警」这类列同样去掉，见 4.7）。
   3. 一本账看板 → **样例⑤**开工，问清显示 🧠 沿用上次口径 2 条（结算时点、客户版规矩）；⑤ 是周报，「较上周变动」的比较基准单独再问，不沿用日报的「上一交易日」。
   4. 需求变更（可选，接在重算之后）：原话末尾加「另外再加一列累计净值，盘中也要能看。」，打开「作为当前需求 #N 的新版本（需求变更）」再开工 → 同一编号另存「需求变更」一版（只用规则时为 v3），需重新确认 3 项，规则参考（以前）80.8 → 150.4 小时。
   5. 纪要直通车：**样例⑥**开工 → 识别到 3 条（研究所 / 风控部 / 资管部）→「拆成 3 条分别受理」→ 切到第 2 条看风控部追保提醒 → 一本账多出 3 行，整段那行标「整段纪要，已拆为 #…」，看板按 3 条算。
   6. 隐盾：**样例③**（投资经理的邮件，夹带客户姓名、资金账号与手机号）开工 → 隐盾页「进模型前脱敏 3 处」与沙箱策略。样例①没有敏感信息，页内另有内置虚构句子的脱敏示例。
   7. Jira：切到「Jira 需求评估」→「上传导出（批量）」→「用示例导出（虚构 14 条）」→ 看汇总与说明行（历史回测：需知 34% / Jira 原估 29%）→ 点 XZ-1040 看「与原估差 +140%」（回测里需知并不比原估准，所以只报差值、不说「原估偏乐观」）→ 点 XZ-1036 看交易链路风险。
3. 配了模型时：开工先出规则初稿，后台增强，页面显示阶段与已等待秒数。看板「估算偏差」只算有效模型估算，要先有一次模型估时、交付后对账才有数；无模型时看下方「规则模板参考 vs 实际」那一行。
4. 网络不稳：`.env` 设 `LLM_MODE=mock` 后重启，Web、REST、MCP、企微全部只走规则（`.env` 的 Key 不再使用，页面上手填的模型照常可用）；没配 `.env` 网关时，页面不填 Key 即全程走规则。

## 4 操作指南：零散需求

### 4.1 录入与口述

- **粘贴**：原话原样贴。带上「来源：企业微信 · 资管运营 小周 → 技术部」这类抬头，来源与提出方会被自动识别。
- **选样例**：六个虚构样例（微信 / 纪要 / 邮件 / Word）：③ 夹带客户姓名、资金账号与手机号，演示隐盾；⑤ 是 ① 同一提出方的第二条，演示追问记忆；⑥ 是一段提了三件事的晨会纪要，演示纪要直通车。切换样例不丢未提交的修改。
- **口述**：点「开始口述」，说完点「结束口述」，识别结果接在原话后面，并纠正常见听错（如「净值日包」→「净值日报」）。语音由浏览器厂商识别，**含客户姓名、账号的内容不要口述**（隐盾只管文字）。
- **参考材料（可选）**：

| 选项 | 用途 | 注意 |
|---|---|---|
| 示例底稿 | 内置「净值日报」页面，出样在原表上插列 | — |
| 上传网页 | HTML 可多选，最多 12 份，单文件取前 400 KB | 「另存为」常得到空壳：F12 复制已渲染的 outerHTML，存成 .html 再传 |
| Git 仓库 | 每行填地址、分支、Token（私有仓）、用户名（Gitee），可加多行 | 只拉 http(s)，拒本机 / 内网与其他非公网地址；浅克隆读完即删，软链接与凭据类文件不读；自建 GitLab 证书不受信可打开「自建 GitLab 证书不受信时跳过 SSL 校验」 |

### 4.2 开工

点「需知，开工」：

1. 先出规则初稿（毫秒级；评测集平均约 0.001 秒）：问清、写单、规则与历史参考、定架、原型同时可看。
2. 模型来源、API Base、Key、模型 ID 齐全时，后台增强自动启动；页面显示阶段与已等待秒数，完成后自动刷新同一条需求。
3. 缺 Key、缺模型 ID 或缺 API Base 时，本次按规则运行，并提示原因。
4. 模型运行中不能重复启动同一操作；可以开新需求，旧任务随后完成也不会覆盖新需求。

每次开工在一本账新记一条，状态「受理」，存为 v1（打开「作为当前需求 #N 的新版本」时例外，见 4.11）。

### 4.3 问清：答复与重算（图：S02_clarify、S03_recompute）

左侧：需求卡片、一句话理解、功能点、抽到的要素、默认假设，以及按影响排序的待确认清单（标影响档、🌾 期货、🧠 沿用、类别，下附「不问会怎样 ｜ 默认」；答复框留空 = 按默认）。右侧：发给业务的确认消息，高影响问题逐条列出，其余写成「没特别要求就按默认」，可复制或「下载确认消息 .txt」。

样例①（资管运营小周：净值日报加一列「较上一交易日变动」、放进风险指标、出客户版）的规则初稿出 12 条待确认：8 条高影响，5 条期货口径（🌾）；配了模型时模型最多再补 4 条，S02 截图即补充后的清单。前三条都是期货口径：T01 以结算后还是收盘价为准、夜盘算哪天；T05 变动比较基准用上一交易日结算价还是收盘价、净值是否复权；T15 客户版脱敏哪些字段、要不要合规审阅。演示答这三条：填入「结算后为准，夜盘算下一交易日」「上一交易日结算价，不复权」「客户版去掉集中度」，点「🔁 按业务答复重算（写单 / 估量 / 定架同步更新）」，提示「已按 3 条答复重算：确认消息、需求单、估量已更新」：

| 项 | 重算前 | 重算后 |
|---|---|---|
| 确认消息里的高影响问题（规则初稿） | 8 条 | 5 条 |
| 业务版需求单 | 「数据与口径」里 T01、T05 标「◻︎默认」 | 改为「✅」并写入答复；「仍待业务确认」少 3 条 |
| 规则模板参考（小时） | 以前 65～145（参考 81）/ 现在 40～90（参考 50） | 以前 65～133（参考 81）/ 现在 40～83（参考 50）：未答高影响题 8 → 5，上界收窄 |
| 一本账 | 受理 · v1 | 已确认 · 新存一版（只用规则时为 v2）；流水记「业务答复重算」「追问记忆」 |
| 追问记忆 | — | 记住 3 条口径（提出方：资管运营） |

重算后结果顶部出现「本次变更」，只用规则时为「v2 · 业务答复重算　相对 v1：已答 +3」；展开「变更明细」看需重新确认项与增删改，可「下载本次变更说明 .md」。答复没变时点重算只提示「答复没有变化，未重算」，不记流水、不存版本。答复里含手机号、账号等隐盾能识别的信息时照常重算，但这几条不记入追问记忆，并提示条数。

规则初稿状态下可点「模型润色」（需先配置模型），在后台进行，已答复和沿用的口径保留。配了模型时，开工和答复重算都先存一版规则结果，后台模型补全后再存一版「模型增强」，所以编号顺延：v1 受理、v2 模型增强、v3 业务答复重算、v4 模型增强；「本次变更」拿 v4 和同样含模型结果的 v2 比，概要同样有「已答 +3」（S03、S14 截图即此情形）。

### 4.4 写单与下载（图：S04_spec_biz、S05_spec_tech）

- **业务版（一页纸，业务签字）**：为什么做、谁用、要做什么、数据与口径（✅ 已答复 / 🔁 沿用 / ◻︎ 默认）、范围外、验收、技术部初判、仍待确认的问题。
- **技术版（用户故事 / 验收 / 字段 / 接口）**：每条用户故事附原话；Given/When/Then 验收；数据字典草案（样例①含 `unit_nav`、`max_drawdown`、`concentration`、`chg_vs_prev` 等）；接口草案；非功能；依赖与假设；范围外。
- 「下载本版 .md」。「转成 Jira 工单去评估」：把需求卡与需求单排成一条 Jira 故事（模块只写主承载平台，需知自己的「数据与渠道复用」分析不写进工单，免得被当成原文多算系统），切到 Jira 评估页直接出结果；文本没改就挂回本条账、不另开一行，改过才按新工单记。

### 4.5 估量：三路依据怎么看（图：S06_estimate_model、S07_estimate_refs）

顶部三张卡并列，下方分别展开：

| 依据 | 来源 | 何时有 | 怎么用 |
|---|---|---|---|
| 独立模型估时 | 模型按本条需求与已读材料拆工作项，逐项估以前 / 现在，附理由、证据与分工 | 配模型且通过校验 | 主要依据，看证据与前提 |
| 规则模板参考 | 六维复杂度 × 手写权重 → 模板小时，公式全展示，标「未校准」 | 始终有 | 查模型是否漏项或多算 |
| 历史记录参考 | 同类历史需求的当时估算、实际工时、开发方式 | 有匹配时 | 只作对照，不套用 |

**独立模型分析**

- 按钮「大模型分析估时」（首次）/「重新分析估时」，后台只重估工时；成功才存一版「模型估时」。
- 「以前（人工开发）」「现在（AI协同）」给区间与参考投入（小时），并注明「预计人时减少 x%」——两边都是估计，不是实测提效。
- 没有可核对的代码证据时显示「粗估」，置信度固定为「低」；有代码证据时置信度最高为「中」。
- 「估算前提与材料范围」写明比较口径：以前 = 熟练开发人员用 IDE、调试器、SQL、自动化测试，不用生成式 AI；现在 = 同等人员使用能检索仓库、改代码、跑测试并迭代修复的编程代理，人负责口径、审查与验收；单位 = 有效人时，无人值守的运行与等待不计。
- 「工作项与估算依据」表：每项标阶段与分工（AI 能做 / AI 做人审 / 人必须做），页面汇总分工占比，并按占比与风险给一句「建议交付方式」；每项可展开「查看依据与证据」。证据只认原话、业务答复、代码摘录三类，且须逐字出现在本次材料里。引号、空白、「AI做人审」这类写法小偏差可容忍；其余不合格时带着校验错误重问一次，仍不合格整份判为不合格、不显示数字。
- 「按阶段对比（小时）」：需求与设计 / 开发 / 测试与比对 / 上线与培训。

**规则模板参考**（展开「规则模板参考 · 六维复杂度、公式与任务」）

- 六维：功能点、数据接入、界面、权限、性能、合规，各 1～5 分并附评分依据，画成六维雷达；权重 1.2 / 1.5 / 1.2 / 0.8 / 1.5 / 0.8，为手写示例，未校准。
- 公式：以前参考小时 = 8 ×［1.5 + Σ 权重 ×（评分 − 1）］；下界 = 参考值 × 0.8；上界 = 参考值 ×（1.4 + 0.05 × 未答高影响题数）；按固定占比分到模板任务（每项标分工），各任务乘固定系数得「现在」，再按分工占比给一句「规则模板建议交付方式（按分工占比，未校准）」。页面按粗参考取整显示（10 小时以上取整数）。
- 样例①（虚构、未校准）：六维 2 / 3 / 2 / 3 / 1 / 3；「各维加进参考工时」为底数 12 + 功能点 9.6 + 数据接入 24 + 界面 9.6 + 权限 12.8 + 性能 0 + 合规 12.8 = 80.8 小时；页面显示以前 65～145 小时（参考 81）、现在 40～90 小时（参考 50），答了前三题重算后为 65～133 / 40～83（S06、S07 截图所示）；交付建议「技术部主做，AI 协同：AI 出初稿、人审关键环节（资金数字、对客内容、交易链路）」。模板预留了数据接入、权限接入等项，可复用时要人工删减；样例①这类「在现有报表上加列」目前仍按新建报表计价——所以它只作参考。
- 只改一个已有指标口径的需求，改用固定工作项模板，不打六维分。

**历史记录参考**（展开「历史记录参考 · 当时估算与实际工时」）：最多 3 条，列编号、类型、相关度、当时估算、实际工时、实际开发方式、来源（虚构演示 / 公司导入 / 台账对账 / 来源未确认）。样例①命中 3 条虚构记录。

**三路不一致时**：① 先看模型工作项是否覆盖原话的每个功能点、有没有重复计时；② 规则模板明显偏高时，看是否预留了本次不需要的项；③ 历史实际工时属于当时的范围和条件，范围不同不直接套用；④ 结论由人判断，写进需求单或 ADR。

### 4.6 定架与 ADR（图：S08_arch_datamap、S09_arch_decisions）

- **复用发现**：对照系统目录给一句结论。样例①（规则初稿）：「报表平台」可部分复用，数据与渠道复用风控系统、估值核算系统、数据仓库。
- **数据地图**：每个数据项定位到「系统 · 数据域 · 接口 · 时效」，标「可复用 / 需申请 / 改动受控 / 需新建 / 时效不符 / 需计算」；盘中、下单前类需求遇到日终或 T+1 数据标「时效不符」。样例①：4 个系统、4 个数据域，可复用 5 项、需申请 1 项（客户与账户信息）、需本需求计算 1 项（较上一交易日变动）。
- 可复用的系统 / 组件、技术栈建议、分层架构图（自动画）。
- **IT 决策**：按需求触发，每项列选项、优点、代价、建议、理由、影响。

| 编号 | 决策 | 触发条件 |
|---|---|---|
| D0 | 基于现有代码 / 底稿改 vs 新建 | 提供了底稿或仓库 |
| D1 | 新建 vs 复用 | 始终 |
| D2 | 数据来源与时点 | 抽到数据来源 |
| D3、D4 | 批处理 vs 实时检测；推送渠道 | 提醒、预警、推送类 |
| D5 | 权限模型 | 页面、报表、涉及客户或权限 |
| D6 | 是否使用 AI 平台 | 公告解析、文案生成等 |
| D7 | 是否改交易链路 | 下单、报单、阻断 |
| D8 | 对外内容与部署 | 涉及客户或对外 |

样例①触发 D1、D2、D5、D8，规则初稿的建议依次是：复用报表平台；数据仓库日终（T+1）；权限按角色 + 产品维度；客户版内网生成、人工发送。「下载 ADR（架构决策记录）.md」含数据地图、现有材料摘要和全部决策。

### 4.7 出样：三种视图（图：S10_proto、S11_proto_client、S12_proto_mobile）

| 视图 | 打开方式 | 区别 |
|---|---|---|
| 内部版 | 默认 | 全部字段；橙色表头是新增列 |
| 客户版 | 页签内「客户版」开关，或开工前打开「原型出客户版（脱敏）」 | 表头含集中度、杠杆、保证金占用，或页面自己标了「内部」的列，一律去掉（「集中度预警」这类写法也算，页面里每张表都处理），规则原型另标「客户版 · 已脱敏」；表格以外的内部指标发客户前人工核对 |

### 4.8 一本账：对账与看板（图：S13_ledger_dashboard）

状态：受理 → 已确认 → 开发中 → 已交付 → 已对账。答复重算会把「受理」自动改为「已确认」；已对账的改回别的状态即撤销对账（清掉实际人天，移出历史记录参考）。

- **对账**：在「要录的需求」选一条（刚开工的已选中），填「实际人天」、是否「用了 AI 协同」及「AI 参与度」、备注，点「对账并回写」。有有效模型估时的会算偏差（用了 AI 的比「现在」，否则比「以前」），并追加到 `data/history_learned.json` 作后续的历史记录参考，不自动校准；没有有效模型估时只记实际。「本条流水」列最近 8 条事件，下方「版本记录」见 4.11；「👍 有用 / 👎 没用」记反馈。
- **需求经营看板**（由台账实时算出）：需求数、平均追问、记忆省问、平均澄清轮次（开工 1 轮 + 每次答复重算 1 轮）、全部台账预计省时（只汇总有效模型估时）、估算偏差（只算有有效模型估时的已对账需求）、出稿用时；图表有各部门需求量、按类型、状态漏斗、按月受理。Jira 规则评估与规则模板参考的偏差各自单列、不计入「估算偏差」，预置数据显示「规则模板参考 vs 实际：平均偏差 29%（7 条已对账；模板权重未校准，演示数据为虚构，与模型估算分开统计）」。部门、类型与追问指标只算零散需求；纪要拆过的整段那行不计入。
- **台账明细**：在「状态」列改好后点「保存状态」；改成「已对账」必须先回写实际人天。「导出审计台账 .csv」不含原话，导出时已防公式注入。
- **催办摘要**（附加，默认不推送）：见 7.4。**模型调用审计**：见 6.6。

### 4.9 追问记忆（图：S15_memory）

- **怎么记**：业务答复并重算后，按「提出方（部门·角色）」和「部门」两级各记一份答复口径。只记答复，不记原话与客户信息；答复里有手机号、账号、客户名等隐盾能识别的信息就不记，并提示「N 条答复含手机号 / 账号等敏感信息，未记入追问记忆」，老库里这类记录也不再沿用。
- **怎么用**：同一提出方再提需求，命中的题自动预填、标「🧠 沿用上次口径」，确认消息单列「这几条沿用你们上次的口径」。口径变了，改掉答复再重算，记忆随之更新。
- **不记的题**：新增列的位置、格式、空值、着色（C_POS / C_FMT / C_NULL / C_SIGN，每条需求的列都不同）、「原话信息不足」的对象题（Q_VAGUE）、模型临时补的题（L 开头）。
- **演示**：样例①答前三题并重算 → 开工样例⑤（同一提出方的净值周报）→ 问清显示「🧠 沿用上次口径 2 条，本次不再问」（结算时点、客户版规矩）；⑤ 的比较基准是「较上周」，按周单独再问（T05W），不沿用日报的「上一交易日」。
- **查看与清理**：一本账页「🧠 追问记忆」表（范围、提出方 / 部门、题号、问题、沿用口径、需求类型、记住时间、沿用次数）；「按提出方清除」后点「清除这一项」，或「清空全部记忆」；企微用 `/记忆 清 <提出方>`、`/记忆 清空`。

### 4.10 纪要直通车（图：S16_minutes_split）

一段会议纪要或长消息里有几条互不相干的需求时，拆开分别受理，每条各自进一本账。单条需求不出现任何提示。

- **切分依据**（纯规则）：行首编号条目（1. / 一、 / ①）、提出方切换（「风控部李经理提出：」）、连接词（「还有一件事」「另外」）。编号只在像纪要、开头说了「几件事」或至少两条编号各带提出方时才切——需求单里的 1. 2. 3. 是同一条需求的功能点；「要求如下：」后面的编号、低一级或缩进更深的编号、「××部补充：」都算上一条的要点。
- **过滤**：背景、参会名单、「下周再议」这类决议不算需求；不足 12 字或只是上一条要点的并回上一条；最多 8 条，不足 2 条按一条处理；来源、时间等抬头每条都带上，参会名单不带。
- **操作**：粘贴整段纪要并开工 → 结果区提示「纪要直通车：这段话里识别到 N 条需求」，列出每条的提出方、预览和拆分依据 → 点「拆成 N 条分别受理」→ 每条按规则各记一行账（流水「纪要拆分受理」），用「查看哪一条」逐条切换，下方各页签跟着换，答复与重算记在各自那行；要模型润色就在切过去的那一条里点。整段那行保留原文，流水记「纪要拆分 · 已拆分为 #…」，台账明细与对账下拉标「整段纪要，已拆为 #…」；看板、首页「已分析需求」和催办摘要按拆出的条数算。
- **样例**：⑥「06_纪要_投研晨会_三条需求」拆出 3 条：研究所仓单库存周报、风控部风险度追保提醒、资管部产品持仓集中度查询页面（看集中度和保证金占用）；参会名单、市场回顾和「下周再议」的夜盘切换安排不算。
- **接口**：REST `POST /api/v1/split`，请求 `{"text": "…", "record": false}`（默认 false 只看怎么拆；true 逐条受理，`results` 里带各自 `req_id`），返回 `count` 与 `segments`（片段已过隐盾），`count` 为 0 表示只有一条需求，照常调 `/analyze`；MCP `xuzhi_split(text, record)`。

### 4.11 需求版本对比与「作为新版本」（图：S14_ledger_versions）

- **版本**：受理、业务答复重算（页面 / 企微 / 接口）、模型增强、模型估时（单独重估成功才记，企微 `/重估` 同理）、需求变更时各存一版快照（要素、待确认、工时、数据地图、决策）；和上一版完全相同时不另存。快照只存原话指纹（哈希），不存原话。Jira 工单不记版本。
- **对比**：一本账选中需求后展开「版本记录（N 版）」，每版标规则初稿还是含模型结果；在「从版本」「到版本」里任选两版（默认最近两版），看功能点增删改、要素、待确认与答复、工时（模型估时只和模型估时比，规则参考只和规则参考比）、数据地图、IT 决策，以及「需重新确认」项（分别找业务、IT、数据负责团队）；「下载变更说明 .md」。
- **本次变更**：存了新版、且屏上正是这一版时，结果顶上出一行「本次变更」；配了模型时和上一份同类结果比（规则初稿比规则初稿、模型结果比模型结果），并注明跳过了哪几版，免得把说法差别当成需求变更。
- **作为新版本**：首页改过原话后，打开开工按钮下的「作为当前需求 #编号 的新版本（需求变更）」再开工，结果追加到原来那条账，而不是新开一条；开关默认关，用完自动复位。
- **样例①**（只用规则时）：答复重算后为 v2（已答 +3）；原话末尾追加「另外再加一列累计净值，盘中也要能看。」并作为新版本开工，得到 v3：需重新确认 3 项（新增高影响的时效问题、D2 数据来源建议改为实时、6 个数据项时效不符），规则参考（以前）80.8 → 150.4 小时。配了模型时编号顺延（见 4.3）。
- **接口**：REST `GET /api/v1/requirements/{id}/versions`、`GET /api/v1/requirements/{id}/diff?from=&to=`（0 = 自动，默认最近两版）；MCP `xuzhi_diff(req_id, from_version, to_version)`。REST / MCP 带同一 `req_id` 发来改过的原话，即记为一版需求变更。

## 5 Jira 需求评估

### 5.1 适用与口径

- 对象：已写好的工单（故事、任务、缺陷、改进、史诗）。不再追问，改做质量检查。
- 计算：目前全部按规则计算（不调模型），每一维都附工单原文依据；结果单位为人天（8 小时 = 1 人天）。目前只在 Web 页提供。
- AI 系数、维度权重为示例值，需按公司 AI 编码工具的实际使用情况校准。

### 5.2 粘贴单条

顶部切到「Jira 需求评估」→「粘贴单条」→ 从 Jira 详情页全选复制，粘进「工单内容」（或「选一个示例工单」）→「评估这条工单」。结果自动记进一本账，提示「已记进一本账 #编号」（同一单号为「已更新」）。

### 5.3 批量导出（图：S17_jira_batch）

1. Jira 筛选结果 → 导出 → CSV（所有字段）；也可另存 Excel（.xlsx）。
2. 「上传导出（批量）」上传文件，或点「用示例导出（虚构 14 条）」。
3. 看汇总：待评估条数（按类型）、传统工时合计、AI 编码工时（编码阶段人工 → AI）、全流程 AI 协同、与原估 / 点数折算偏差 ≥ 40% 的条数；说明行写团队系数、校准样本构成与历史回测；下方按单号的编码阶段柱状图。示例导出：待评估 5 条（需求 3 / 缺陷 1 / 任务 1），另有史诗 1 条单列、不计入合计；历史回测「需知 MAPE 34% / Jira 原估 29%」。
4. 「逐条结果」点一行看详情（已完成的工单也列出，可对照实际耗时）；「导出评估结果 .csv」（已防公式注入）。

### 5.4 字段识别规则

| 来源 | 识别规则 |
|---|---|
| 粘贴文本 | 单号（如 XZ-1024，只在前 3 行找；UTF-8、SHA-256 这类不当单号）；行内字段「类型」「优先级」「模块」「Story Points / 故事点」「原始预估」「剩余预估」「实际耗时 / 耗费时间」；段落「描述」「验收标准 / AC」「技术说明」「复现步骤」「期望结果」；没有验收段时，描述里的 Given / When / Then 也算 |
| 导出表头 | 中英文均可：问题关键字 / Issue key、摘要 / 概要 / Summary、问题类型、状态、优先级、模块 / Component/s（同名多列合并）、标签、描述、Story Points（含「自定义字段 (Story Points)」）、原始预估 / 预估工时、剩余预估、耗费时间 / 实际工时 / Time Spent、验收标准 / Acceptance Criteria 列 |
| 时间 | 导出的时间列按秒折算小时（表头含「小时」「(h)」「hours」时按小时，含「人天」「days」时按人天）；粘贴文本认 3d 4h、16h、2天、1.5 人天、2人日、1w |
| 忽略 | Σ 开头的汇总列；父级 / 子任务 / 史诗列；经办人、报告人、验收人等人名字段一律不读 |
| 编码 | CSV 自动识别 UTF-8 / GB18030 |

### 5.5 结果怎么读（图：S18_jira_detail）

| 结果 | 口径 |
|---|---|
| 类型 | 由问题类型判为缺陷 / 任务 / 需求 / 改造，基线 0.6 / 1.0 / 1.5 / 2.5 人天 |
| 技术复杂度（六维） | 改动规模、涉及系统、数据与口径、接口与性能、测试与验收、风险与依赖，各 1～5 分；合计 ≤ 10 低、≤ 14 中、≤ 19 高，其余很高。「结算系统」里的「结算」、「不改表结构」这类否定说法不误判 |
| 传统工时 | 类型基线 + 六维加权 → 乘团队系数 → 与同类型、相似度 ≥ 0.5 且至少共享 2 个业务名词的已完成工单类比（各占一半）；下界 × 0.8，上界随风险项放宽 |
| AI 编码工时（主数） | 只算编码阶段：编码实现、单元测试、自测联调、代码评审（缺陷另含定位排查），逐项乘 AI 系数；触及交易链路的编码只按「AI 做人审」折算 |
| 全流程 AI 协同 | 设计、编码、测试、上线全部任务合计 |
| 对比原估 | 有原始预估直接比；只有故事点时按已完成工单折算「1 点 ≈ x 人天」再比（「Jira 原估」与「故事点折算」分两列）；差 ≥ 40% 标出来。只有历史回测（已完成工单逐条留一法，至少 3 条）显示需知误差低于 Jira 原估时，才写「原估偏乐观 / 偏保守」，否则只写「与原估差 +x%」并附回测误差；原估不到 1 天、需知也不到 1.5 天的小单只报差值 |
| 质量检查 | 缺验收标准或太少、缺陷没写复现 / 期望、没写涉及模块、触及交易链路、涉及客户数据、有对外客户版要合规审阅、提性能没给指标、提到夜盘 / 节假日 / 换月 / 结算但验收没场景、史诗或超 10 人天该拆 |
| 置信度 | 工单完整且有相似已完成工单为高；缺验收且无相似工单为低 |

示例导出（虚构）里，XZ-1040 显示「与原估差 +140%（历史回测：需知误差 34%，原估 29%）」——回测里需知并不比 Jira 原估准，所以页面只报差值、不说「原估偏乐观」；XZ-1036 标「触及交易链路：须走变更评审与下单回归，编码只按「AI 做人审」折算」。

### 5.6 记账与校准

- 每条评估记一行一本账（来源 Jira）；同一单号再评只更新数字，流水记「Jira 重新评估」；已对账的行再导入只留痕、不覆盖；工单原文先过隐盾再存。
- 状态随 Jira：待办 → 已确认，进行中 / 测试 → 开发中，完成 → 已交付；Jira 里已完成且有耗费时间的，自动按实际耗时对账。
- 校准样本：评估自己的工单只用 `data/jira/历史/` 下的导出（`.csv` / `.xlsx`，含耗费时间）和一本账里对过账的自己的工单，一条虚构示例都不混；评估示例时只用示例里已完成的 8 条（虚构，说明行注明「示例」）。已完成的工单也评一遍，但按留一法，不拿自己校准自己。不足 3 条不校准；团队系数取「实际 ÷ 规则」的中位数，限制在 0.5～2.0；对账时勾了「用了 AI 协同」的不进校准样本。对过账的工单成为下次评估的校准样本（Jira 线自己的回写），不写进零散需求的历史库。

### 6.2 自定义网关（公司 AI 平台）

1. 模型来源选「自定义网关（如公司 AI 平台）」。

### 6.3 .env 字段

REST、MCP、企微入口、`run_demo.py`、`检查接入.command` 不经过页面，模型只读本机 `.env`。复制 `.env.example` 为 `.env` 再改；`.env` 已 gitignore；系统环境变量优先于 `.env`。

| 变量 | 默认 | 作用 |
|---|---|---|

| `XUZHI_HISTORY_LEARNED` | 一本账同目录的 `history_learned.json` | 对账回写的历史记录参考 |

### 6.4 超时与失败

| 情况 | 行为 |
|---|---|
| 连不上 | 10 秒放弃 |
| 单次超时 | `LLM_TIMEOUT`（默认 90 秒），不自动重试 |
| 超时或连不上之后 | 120 秒内本次其余模型步骤直接走规则，不再逐步等超时 |
| 估时格式不合格 | 带着校验错误重问一次；仍不合格提示「模型输出格式不合格：原因；可直接重试。」，不显示数字 |
| 输出被截断 | 「模型输出被截断（max_tokens 不足或材料过多），尚未生成工时…」；调大 `LLM_MAX_TOKENS`、减少材料或换支持长输出的模型 |
| 出站仍有明文敏感项 | 按 `sandbox.yaml` 拒发，该步回退规则结果；估量页提示「出站内容含明文敏感项，已按沙箱策略拒发，尚未生成工时…」 |
| 所选模型在网关无渠道 | 「当前网关没有为所选模型提供可用渠道…请读取可用模型目录…」 |
| 后台任务失败 | 保留快速结果，提示「模型后台处理失败，快速结果已保留…」；异常原文不展示（可能含网关地址或认证信息） |

### 6.5 无 Key 时各入口的行为

| 入口 | 行为 |
|---|---|
| Web | 规则初稿、规则模板、历史参考、需求单、定架、原型全部可用；估量卡显示「尚未调用模型」，不显示加载状态 |
| REST / MCP | `polish` 默认 false 即规则；polish=true 但 `.env` 未配也退回规则；返回 `estimate.status = "unavailable"`，以前 / 现在为空，`references` 照常 |
| 企微 | 回复「工时：暂无模型估时（未接入模型）」，并附规则模板与历史参考 |

### 6.6 模型调用审计（图：S20_audit）

每次经 `xuzhi/llm.py` 发出的模型调用都记一行（与一本账同库，表 `llm_calls`）：

| 字段 | 说明 |
|---|---|
| 时间、用途 | 问清润色 / 写单润色 / 估时分析 / 出样改稿 |
| 渠道、后端 | Web / 企微 / API / MCP / 命令行；openai / qoder-cloud |
| 网关主机、模型 | 只记主机名，不记 Key 与完整地址 |
| 耗时、提示词字数、回复字数 | — |
| 出站脱敏标签 | 提示词里 `<手机_1>` 这类标签个数，证明进模型前过了隐盾 |

### 7.1 企业微信

同事在企业微信里 @需知 发一段原话，需知跑完「隐盾 → 问清 → 写单 → 估量 → 定架」，把要确认的问题、工时、拍板项回到聊天里，按编号回答即可重算。长连接由本机主动连出，内网不需要公网回调地址。

**路由**（14 个）：

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/api/v1/health` | 存活、知识库规模、模型模式、沙箱摘要（不需 Token） |
| POST | `/api/v1/analyze` | 整条链：卡片、清单、确认消息、估量、定架、需求单 |
| POST | `/api/v1/clarify` | 只返回问清 |
| POST | `/api/v1/split` | 纪要拆分（见 4.10） |
| GET | `/api/v1/requirements?n=20` | 一本账最近 n 条（1～200） |
| GET | `/api/v1/requirements/{req_id}` | 单条 + 流水 |
| GET | `/api/v1/requirements/{req_id}/versions` | 历次版本（版本号、时间、动作、快照） |
| GET | `/api/v1/requirements/{req_id}/diff?from=&to=` | 两版差异、需重新确认项与变更说明（见 4.11） |

| GET | `/api/v1/audit/llm?n=50` | 模型调用审计 |
| GET | `/api/v1/sandbox` | 沙箱策略与执行位置 |

**analyze / clarify 请求体**：`text`（必填）、`source`、`answers`（问题 id → 答复）、`req_id`（答复重算时传上次返回值）、`polish`（默认 false；true 用服务端 `.env` 模型，同步执行，只跑要返回的部分：analyze 做问清润色与模型估时，`include_spec` / `include_prototype` 为 true 才润色需求单、改原型；clarify 只做问清润色）、`record`（默认 true）、`include_spec`（默认 true）、`include_prototype`（默认 false）、`mobile`、`client_view`。analyze 返回卡片、清单、确认消息、`estimate`（`before` / `after` 为小时，`references` 为规则与历史两路参考；模型结果另带比较口径 `comparison`、分工 `who`、建议交付方式 `delivery`）、`architecture`、`spec` 等。

**req_id 规则**：带 `answers` + 上次的 `req_id` = 业务答复重算，同一条账更新并写追问记忆；带 `req_id` 不带答复、原话也没改时不算一轮澄清，只在拿到有效模型估时后写回（存「模型估时」一版），不会清掉已有估时；原话改了 = 需求变更。编号不存在返回 404，Jira 工单那行返回 422（请在 Jira 评估页重评），已对账的需求只读。

```bash
B=http://127.0.0.1:8770/api/v1
curl $B/health
# 受理一条需求（规则引擎）
curl -X POST $B/analyze -H 'Content-Type: application/json' \
  -d '{"text":"资管运营小周：净值日报能不能加一列较上一交易日变动，风险指标也放进去，周五给客户那版也要。"}'
# 业务答复后重算：带同一段原话、上次的 req_id，问题 id 取自上次返回的 questions[].id
curl -X POST $B/analyze -H 'Content-Type: application/json' \
  -d '{"text":"（同一段原话）","req_id":1,"answers":{"T01":"结算后为准，夜盘算下一交易日"}}'
curl -X POST $B/requirements/1/status -H 'Content-Type: application/json' -d '{"status":"已交付"}'
curl -X POST $B/requirements/1/reconcile -H 'Content-Type: application/json' \
  -d '{"actual_days":6,"ai_assisted":true,"ai_share":0.5,"note":"范围多了客户版"}'
curl "$B/digest?fmt=markdown"
curl -H 'Authorization: Bearer <XUZHI_API_TOKEN>' $B/requirements   # 配了 Token 时
```

Windows PowerShell 请用 `curl.exe`，或直接在 `/docs` 页面试调。

**鉴权与监听**：默认只听 127.0.0.1（`sandbox.yaml` 的 `api.bind`）；对外须设 `XUZHI_API_HOST`（或 `--host`）且必须配 `XUZHI_API_TOKEN`，否则拒绝启动；配了 Token 后，除 `/api/v1/health` 外（含 `/api/v1/sandbox`）都要带 `Authorization: Bearer <token>` 或 `X-API-Token: <token>`，Token 按恒定时间比较，不对返回 401。端口改 `XUZHI_API_PORT`。请求体不接受模型 Key，模型只用服务端 `.env`。接口本身是 HTTP，对外请放在公司网关之后。

### 9.2 隐盾规则

本地正则，不联网。命中的内容换成语义标签，模型输出再还原；同一原文在多份材料里用同一标签，新标签接着编号，免得还原错位。

| 类别 | 规则 | 标签 |
|---|---|---|
| 身份证 | 18 位（含 6-8-4 分段写法），校验出生日期段 | `<身份证_1>` |
| 手机 | 1 开头、第二位 3～9 的 11 位，可带 +86，允许空格 / 横线分段 | `<手机_1>` |
| 座机 | 0 开头区号 + 横线 + 7～8 位，可带分机 | `<电话_1>` |
| 邮箱 | 常见邮箱格式 | `<邮箱_1>` |
| 账号 | 10～19 位连续数字；4-4-4-4 分组银行卡；「资金账号 / 账号 / 卡号 / 客户号」等后面的 6～9 位短号 | `<账号_1>` |
| 内网地址 | 10.x、192.168.x、172.16～31.x | `<内网地址_1>` |
| 密钥 | api_key / token / secret / password / 密码 后跟冒号或等号与 6 位以上字符 | `<密钥_1>` |
| 金额 | 带两组以上千分位的数字 | `<金额_1>`（审计不计入明文敏感项） |
| 客户 / 机构 | 「客户 / 投资者 / 机构」后的机构名（以公司、基金、期货、证券、银行、信托、私募等结尾）；「客户 / 投资者」后的姓名；「×先生 / ×女士」（不必带「客户」，如「张先生」）；紧挨在手机 / 账号 / 证件号前的姓名。同事称谓（王总、张老师、李经理）不算 | `<客户_1>`、`<机构_1>` |

样例③脱敏后为 `客户<客户_1>先生（资金账号 <账号_1>，手机 <手机_1>）`，隐盾页显示「进模型前脱敏 3 处」。局限：没有上下文提示词的人名、机构名可能漏掉，也可能多遮；审计里的明文敏感项计数同样只反映这些规则能识别的类型，不等于零泄露。正式使用前用脱敏后的真实样本跑评测集的 `redact_must_not_contain` 检查。隐盾只处理文字，口述语音在识别前已到浏览器厂商。

### 9.3 什么会离开本机

| 去向 | 何时 | 内容 |
|---|---|---|
| 模型网关 | 配置模型后 | 脱敏后的原话、答复、HTML 底稿与代码摘录（连同文件名、标题、表头、目录）；出站前再查一遍，仍有隐盾能识别的明文就拒发；`.env` 的 Key 只发往 `.env` 里同一个网关 |
| Git 托管平台 | 填了仓库地址 | 浅克隆请求（Token 走请求头，跨主机跳转不带） |
| 浏览器语音服务 | 使用口述 | 语音 |
| 企业微信 | 启用企微入口 | 长连接 `wss://openws.work.weixin.qq.com` 与回复内容（不回显原话，答复回执已脱敏） |
| 企微群 webhook | 开启催办推送 | 数量、标题、天数 |
| 问码网关 | 使用 `/问` | 需知源码片段与问题（不经隐盾） |
| pip 源 | 首次安装 | 依赖下载 |

一本账、追问记忆、审计记录、版本快照与 `.env` 文件不离开本机。

## 10 常见问题与排错

| 现象 / 提示 | 原因与处理 |
|---|---|
| 「未找到 Python 3.10 或更高版本」（Windows） | 安装 Python 3.12 并勾选「Add python.exe to PATH」，或确保 `py` 启动器可用 |
| 「安装依赖失败。请检查网络后重新双击本脚本。」 | pip 源不通；换网络或配置公司 pip 镜像后重试 |
| Mac 双击 `.command` 打不开 | 在系统设置里允许打开，或在终端对脚本执行 `chmod +x`；确认 `python3 --version` ≥ 3.10；装错版本时删掉 `.venv` 重来 |
| 局域网其他电脑打不开页面 | 设计如此：页面只听 127.0.0.1（`.streamlit/config.toml`），且没有登录；多人使用先放到带鉴权的反向代理后面，再改 `server.address` |
| Key 框是空的，状态灯却显示「模型已配置」 | 正常：`.env` 的 Key 只在服务端使用、不放进页面控件（框内提示「已用本机 .env 的 Key（页面不显示）」），也只发往 `.env` 里同一个网关；页面改了网关就不再带它。临时只走规则：`.env` 设 `LLM_MODE=mock` 后重启 |
| 「未填 Key → 本次先出需求初稿…」/「未填模型 ID…」 | 正常：本次按规则运行；补齐后在「问清」点「模型润色」，或在「估量」点「大模型分析估时」 |
| 「拉取实时目录失败：HTTP 401 …」/「账号当前无可用模型（目录为空）」 | Key 错误或账号无可用模型；目录为空时可手填模型 ID |
| 「API Base 须以 http:// 或 https:// 开头」/「网关协议…不在沙箱策略允许范围」 | 改正网关地址；协议白名单见 `llm.allowed_api_schemes` |
| 「当前网关没有为所选模型提供可用渠道…」 | 点「读取可用模型」，按账号支持的模型重选 |
| 「模型输出格式不合格：…；可直接重试」 | 模型返回不合格（缺证据、引用对不上、区间不合理），程序已带着校验错误重问过一次；「重新分析估时」或换模型 |
| 「模型输出被截断（max_tokens 不足或材料过多）…」 | 调大 `LLM_MAX_TOKENS`（或留空按网关默认）、减少参考材料，或换支持长输出的模型 |
| 「模型网关超时或连不上…」/ 长时间「模型正在分析」 | 网关慢或断；先看规则结果，稍后重试，或调大 `LLM_TIMEOUT` |
| 「出站内容含明文敏感项，已按沙箱策略拒发…」/ 审计错误摘要「沙箱策略拒发：出站提示词含 N 处明文敏感项…」 | 默认开启的保护：出站提示词里仍有隐盾能识别的明文，该步不发、回退规则结果。检查原话、答复与材料里的手机号、账号等；不建议为演示关掉 |
| Git：「仓库地址只支持 http:// / https://（不支持 file://、ssh、git@）」「仓库地址里不要带用户名 / 密码…」 | 改成 `https://主机/组/仓.git`，Token 填在旁边的输入框 |
| Git：「仓库地址指向本机 / 内网地址…」/「本机代理开着 fake-ip 模式…」 | 设计如此，不拉内网；公网托管域名可加入 `repo_fetch.fake_ip_trusted_hosts` 或在代理里设直连 |
| Git：「仓库地址发生跳转，请直接填写最终的 https 地址」 | git 不跟随跳转；填跳转后的最终地址 |
| Git：SSL 握手失败 | 打开「自建 GitLab 证书不受信时跳过 SSL 校验」，或设 `XUZHI_GIT_SSL_NO_VERIFY=1` |
| 「当前浏览器不支持口述」/「未获得麦克风权限」/「语音识别需要网络」 | 用 Chrome / Edge，在地址栏允许麦克风，确认能联网 |
| 「这些编号改成「已对账」但没有实际人天，未保存」 | 先在上方对账表单回写实际人天（须大于 0） |
| Jira：「没从文件里读到工单…表头含「摘要」或「Summary」」 | 用 Jira 原始导出，不要删表头 |
| Jira：「已完成工单只有 N 条，不足 3 条，按规则模型（不校准）」 | 把含耗费时间的历史导出放进 `data/jira/历史/`（页面缓存 10 分钟） |
| 导入：「找不到标题列，现有列：[…]」 | 把标题列改成 8.3 表里的列名之一 |
| 改了 `sandbox.yaml` 或知识库没生效 | 重启对应进程；隐盾页提示「未安装 PyYAML」时执行 `pip install pyyaml` |
| REST：「拒绝启动：监听非本机地址必须配置 XUZHI_API_TOKEN」 | 配 Token，或改回 127.0.0.1 |
| REST：401 / 404 / 422 | 未带或带错 Token（配了 Token 后 `/sandbox` 也要带）/ 编号不存在 / 状态值或原话不合法（「已对账」请走 reconcile；Jira 工单那行请在 Jira 评估页重评） |
| MCP：「需知 MCP 服务需要 mcp 1.x…」 | `pip install -r requirements-api.txt`（已锁 `mcp<2`） |
| MCP：「拒绝启动：MCP HTTP 只允许监听本机…」 | 只在本机监听；确需对外放网关后并设 `XUZHI_MCP_ALLOW_EXPOSED=1` |
| MCP：对外后请求返回 421 | 在 `XUZHI_MCP_ALLOWED_HOSTS` 写网关转发时带的 Host |
| 企微：启动即打印「缺少企微机器人凭据」 | 在 `.env` 填 `WECOM_BOT_ID`、`WECOM_BOT_SECRET`、`WECOM_ALLOW_USERS` |
| 企微：「未授权：用户 xxx 不在白名单」 | 发 `/whoami` 查 userid，加入 `WECOM_ALLOW_USERS` 后重启 |
| 企微：连接反复断开 | 同一机器人只允许一条长连接，关掉其他进程 |
| 企微：「模型响应慢，这次没等到结果…」/「模型估时未成功：…；发 /重估 再试」 | 发 `/重估` 在同一条账上再估一次；仍慢可调 `WECOM_ANALYZE_TIMEOUT`，或去 Web 端看规则初稿 |
| 企微：「排队超时了」/「需求太短了」 | 稍后再发；太短时发完整原话（不少于 15 字） |
| 企微问码提示配置 `ANTHROPIC_*` | 问码与需求分析是两套接口，见 7.1 |
