## 一句话

**一堆话进来，一份能开工的需求出去。**
投资经理在企业微信里说的三句话、晨会纪要里的一段、一封邮件，原样扔进「需知」，五分钟内业务同事拿到一张"要确认的事"清单和一个能点的原型页，技术部拿到需求单、工时、要拍板的技术决策和数据从哪取；需求从受理到交付记在一本账上，交付后回写实际工时，下次估得更准。

## 1. 问题：技术部与业务之间最贵的不是写代码，是"说清楚"

投资、资管、研究条线向技术部提需求，今天的常态是：需求来时是口语，澄清要三四轮微信；工时靠经验拍，排期反复调；新建还是复用、数据从哪取、实时还是日终这些技术决策往往开工后才暴露，造成返工；需求改了没人记；结算时点、夜盘归属、主力合约切换、三套限仓口径、保证金加收比例、客户信息脱敏这些期货行业特有口径最容易被漏，上线后数字对不上。

这不是某一个部门的问题，而是全公司需求受理环节的共性痛点。按技术部【2026 年 1～8 月】的受理情况【抽样 N 条】：

| 指标 | 现状（待校准） | 口径 |
|---|---|---|
| 一条需求从提出到"说清楚"的澄清轮次 | 【3～4】轮 | 微信 / 邮件往返次数 |
| 需求文档产出时间 | 【1～2】天 | 从提出到技术版需求单 |
| 工时估算偏差 | 【±40%】 | 估算 vs 实际人天 |
| 因需求不清导致的返工占比 | 【a%】 | 上线后返工工单 / 全部工单 |
| 业务确认周期 | 【c】天 | 需求单发出到业务签字 |

（以上五个数字建议用一页问卷 + 工单抽样在 10/10 前校准；没有的项用"技术部 5 人经验估计"标注，不编。）

## 2. 方法：需求分析六步法

我们先把"怎么把需求说清楚"沉淀成一套六步方法，再把它做成工具。方法本身不依赖工具，任何部门、任何子公司的技术团队拿去就能用——这是可复制的第一层。

| 步 | 名字 | 做什么 | 产出 | 谁看 |
|---|---|---|---|---|
| 1 | **问清** | 从原话抽出目标、角色、触发、频率、数据、渠道、非功能项；对照"期货 IT 需求追问知识库"生成待确认清单，每条附"不问会怎样"和默认假设 | 待确认清单 + 一键发业务的确认消息 | 业务答，技术看 |
| 2 | **写单** | 双版需求单：业务版一页纸（能签字）+ 技术版（用户故事、验收标准、数据字典、接口草案），技术条目回链业务原话 | 需求单 | 业务签，技术干 |
| 3 | **估量** | 双轨估算：六维复杂度 + 历史需求类比 → 传统人天；需求拆成任务，逐项标"AI 能做 / AI 做人审 / 人必须做" → AI 协同人天、省时比例、建议交付方式 | 工时区间 + AI 分工表 | 领导排期 |
| 4 | **定架** | 复用发现（对照系统目录）、数据地图（每个数据项定位到 系统 · 数据域 · 接口 · 时效）、IT 决策清单（选项 / 建议 / 影响）→ 架构决策记录 | ADR | IT 拍板 |
| 5 | **出样** | 按需求单自动生成可点的原型页；有现成页面底稿就在原页上改，业务改一句话原型跟着变 | 原型页（内部版 / 手机版 / 客户脱敏版） | 业务确认 |
| 6 | **对账** | 需求进一本账：受理 → 已确认 → 开发中 → 已交付 → 已对账；交付后回写实际人天，写入历史需求库，估算自动校准；看板汇总各部门需求量、澄清轮次、估算偏差、AI 协同省时 | 需求一本账 + 经营看板 | 部门管理 |

贯穿六步的一道门是**隐盾**：原话、上传的页面底稿、代码摘录进模型前先在本地脱敏，输出再还原。

## 3. 产品：「需知」是六步法的数字化载体

「需知」（XuZhi）是一个网页工作台，六个标签页对应六步；左上角选模型、填 Key，不填 Key 也能跑完整条链（规则引擎兜底，毫秒级出稿）。

**业务同事的一天**（Demo 样例，均为虚构）：资管运营小周在企业微信说"净值日报能不能加一列'较上一交易日变动'，风险指标也放进去，周五给客户那版也要，最好下周就能用"。技术部把这段话贴进需知，30 秒后：

- 问清：12 条待确认，按影响排序——变动的比较基准是上一交易日结算价还是收盘价？客户版要脱敏哪些字段？风险指标具体要哪几个、公式沿用风控系统吗？历史要回填吗？……每条给了默认假设，小周只答不同意的。
- 写单：业务版一页纸给小周签字；技术版 4 个用户故事、验收标准、数据字典（unit_nav / max_drawdown …）、接口草案给开发。
- 估量：传统开发 8.5 人天（六维加权 + 3 条相似历史需求校准，置信度中），AI 协同 5.4 人天（省 36%）；任务表标出哪些让 AI 做、哪些必须人做、哪些 AI 做人审（涉及客户版内容的不打折）。
- 定架：报表平台可承载、估值核算与风控系统数据可复用；数据地图：产品净值 ← 估值核算系统（T+1，视图可用），风险指标 ← 风控系统（日终表可用），客户信息 ← 客户管理系统（需申请字段权限），"较上一交易日变动"需本需求计算；3 项要 IT 拍板（复用 vs 新建、数据时点、权限模型），ADR 自动生成。
- 出样：一张带假数据的净值日报原型，客户版自动隐去内部字段；小周说"变动列放净值旁边"，原型跟着改。
- 一本账：这条需求进账，状态"受理"；交付后填实际人天，下次遇到"日报加列"类需求，估算就有了真实参照。

## 4. 创新点：比"AI 写 PRD"多出的五层

1. **问的是期货问题，不是软件问题**。36 条"期货 IT 需求追问规则"（结算时点与夜盘、主力合约切换、交割月、三套限仓口径、保证金加收、涨跌基准、单位与精度、客户版脱敏与适当性……）由触发词驱动，通用工具（spec-kit 的 clarify、BMAD 的 analyst）问不出这些；原话不像期货业务时自动不套期货模板（评测集里财务报销、培训签到两条误问率 0）。
2. **双轨估算，把 AI 写进工时**。传统口径之外，每个任务标 AI 能做 / AI 做人审 / 人必须做并乘协同系数，给出 AI 协同人天与建议交付方式（技术部主做，还是业务在公司 AI 平台自建、技术部只审核）——契合"人人都有智能体"。
3. **数据地图，回答"数据从哪取"**。系统目录不只是名字，而是每个系统持有的数据域、接口与时效；需求里每个数据项定位到具体系统与接口，盘中 / 下单前类需求自动检查时效够不够，需要新建或申请的一眼看清。
4. **决策前置，告诉领导要拍板什么**。新建 vs 复用、数据时点、批处理 vs 实时、推送渠道、权限模型、是否用 AI 平台、是否改交易链路、对外内容管控——每项 2～3 个选项 + 建议 + 影响，架构评审从开工后提到需求阶段。
5. **一本账闭环，估算越用越准**。需求从受理到交付全程留痕；对账回写实际人天进历史需求库，形成估算飞轮；看板把"各部门提了多少、澄清几轮、估得准不准、AI 省了多少"实时算出来——工具变成数据产品。

## 5. 技术方案

**架构**：Streamlit 网页 + Python 流水线（隐盾 → 问清 → 写单 → 估量 → 定架 → 出样）+ SQLite 一本账；四层知识：规则引擎（类型 / 触发 / 频率 / 非功能 / 数据源词典）、行业知识库（36 条追问规则）、系统目录（13 系统、16 数据域、23 接口，虚构示例）、历史需求库（30 条，虚构；对账回写另存 `history_learned.json`）。

**规则与模型的分工**：数字全部由程序算（复杂度、人天、相似度、数据地图、看板），大模型只负责组织语言与补充追问、按底稿改原型；无模型时整条链完整可跑，有模型时按钮触发润色。模型通过公司 AI 平台的 OpenAI 兼容接口调用（页面选模型、填 Key，Key 只留会话），也支持 Qoder Cloud 与自定义网关。

**开源借鉴**：需求与架构模板借鉴 BMAD-METHOD、spec-kit（MIT），变更提案思路借鉴 OpenSpec（MIT），多角色 SOP 思想借鉴 MetaGPT（MIT）；核心流水线、期货追问知识库、双轨估算、数据地图为自研，不引入 Commons Clause 限制的代码。

**质量**：62 项自动化测试；20 条评测集跑分（见第 6 节）；出样支持上传现有页面 HTML 或填 Git 仓库地址，在原页上增量改。

**部署**：Python 3.10+，单机可跑（`streamlit run app.py`），无外部依赖；接入公司 AI 平台只需网关地址与 Key；真实知识库用本机导入工具从 xlsx 模板导入，不经过任何外部服务。

## 7. 技术与落地可行性

不接生产数据库、不改任何现有系统，纯文本进出；单机部署，无外部依赖；没有模型也能跑，模型只做润色，网关不通自动退回规则；62 项测试、20 条评测集把行为钉住，改规则退化会红；真实知识库三张表（历史需求、追问规则、系统目录）从 xlsx 模板一键导入，工单系统导出也能直接吃；出样可基于现有页面 HTML 改，不用重画。

上线路径：第一阶段技术部内部用（受理入口），第二阶段业务部门自助提交（先问清再找技术部），第三阶段接公司 AI 平台账号体系与工单系统（一本账与工单双向同步）。

## 8. 可复制推广性

方法（六步法）本身零成本推广。工具层面，需知不依赖任何业务系统，换三张表即可换一个单位：追问规则按行业换（证券、租赁、资管各一套），系统目录按公司换，历史需求库按团队攒；总部各部门、分公司、子公司的技术团队都能用，集团层面可把追问规则做成共享知识库。四类角色都受益：提需求的业务同事（自助说清）、受理的技术人员（少澄清少返工）、排期的领导（工时有依据、决策前置）、部门管理（需求经营看板）。

## 9. 安全与合规管控

数据去向写在界面上。原话、上传的页面底稿、仓库代码摘录进模型前一律经本地规则脱敏（手机号、账号、证件号、内网地址、密钥、客户与机构名 → 语义标签），模型输出再还原；凭据类文件（.env、*.pem、*secret*）不读。不接生产数据库；Git 仓库只在使用者主动填地址时浅克隆，只放行 http(s)、拒绝本机与内网地址，Token 走环境变量不进命令行与配置；原型预览在独立源的沙箱 iframe 里渲染，页面脚本读不到需知本页。模型调用走公司 AI 平台，Key 只留会话；浏览器口述功能在界面提示"语音会送到浏览器厂商，含客户信息勿口述"，正式环境接公司语音服务。每次分析、答复、状态、对账写入一本账，可导出审计 CSV。演示数据全部虚构。
