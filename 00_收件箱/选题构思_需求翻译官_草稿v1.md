# 方案乙 · 选题构思 v1 —— 「需知」需求分析智能体（需求翻译官）

> 2026-09-08 ｜ 草稿。Jerry 定：团队赛做一个**通用一点的需求分析工具**——"一堆话扔进去，先出一版，告诉你要和业务确认什么、复杂度、工时、需要 IT 决策的技术栈架构"；要功能性强、有创新性和亮点；套壳或借鉴开源都可以。
> 本文：定位 → 场景故事 → 产品与技能 → 六个亮点 → Demo → 开源底座 → 五维 → 合规 → 赛别与组队 → 评测与成效口径 → 计划 → 待 Jerry 定的事。

## 0. 一句话

**「需知」：一堆话进来，一份能开工的需求出去。**
微信三句话、一段会议纪要、一封邮件、一次语音转写——扔进去，它先出一版需求，然后告诉你：**要和业务确认哪 8 件事、这活多复杂、大概多少人天、有哪几处要 IT 拍板（新建还是复用、数据从哪取、批还是实时、权限怎么做）**，顺手把可点的原型页也画出来给业务看。业务改了三句话，它告诉你改了什么、影响多少工时、要重新确认什么。

**为什么是它**
- 技术部与投资 / 资管 / 研究员之间最费劲的不是写代码，是"说清楚"：需求来时是口语，澄清要三四轮，工时靠拍脑袋，选型靠个人经验，需求改了没人记。
- 通用（任何部门提需求都能用 → 可复制满分），又能做深（期货业务的追问规则、公司系统复用目录、历史工时校准 → 创新分）。
- 纯文本进出、不碰生产系统、全内网 API → 落地与安全都好讲；Demo 全用虚构需求。
- Jerry 擅长写会议纪要——"纪要 → 需求"正是它的一条主入口。

## 1. 场景故事：技术部的一天（四个真实入口，也是 Demo 的四个样例）

| 入口 | 谁、怎么来的 | 原话（虚构样例） | 现在怎么熬 | 有了「需知」 |
|---|---|---|---|---|
| ① 微信 | 资管运营 | "净值日报能不能加一列'较上一交易日变动'，风险指标也放进去，周五给客户那版也要，最好下周能用" | 开发问：哪些产品？复权口径？结算后多久出？客户版要脱敏吗？历史要回填吗？——三天四轮微信 | 30 秒出待确认清单 8 条（按影响排序，附默认假设与"不问会怎样"）+ 一键生成给运营的确认消息；估 3～5 人天；指出"现有报表平台可复用，加模块即可" |
| ② 会议纪要 | 研究员（晨会纪要一段） | "想做一个基差监控页面，主要品种都要，异常了要提醒，最好手机能看" | 纪要里没说现货价格从哪来、主力合约怎么切换、什么叫异常、提醒发哪、夜盘算不算 | 追问清单直接列出上述 6 条**期货特有问题**；出业务版一页纸 + 技术版用户故事；估 10～15 人天；架构决策 3 项（现货数据源、实时 vs 定时、推送渠道） |
| ③ 邮件 | 投资经理 | "下单前能不能自动提示一下会不会超限仓，别等交易所拒单了才知道" | 限仓口径三套（交易所 / 公司 / 产品合同）、实时还是结算后、提示还是阻断、和交易系统事前风控什么关系——没人先想清楚就开工，返工 | 待确认清单把口径、时点、阻断策略、与现有风控边界全部列出；复用发现："交易系统已有事前风控，建议做解释与缺口测算而非重建" |
| ④ 大需求 | 风控部（一页 Word） | 交易所调保证金 / 限仓时自动测算逐产品逐客户影响并通知 | 大需求最怕估不准：拆不细、依赖没理、哪些要领导拍板不清楚 | 拆成 4 个模块 22 个任务，依赖图与里程碑；工时区间 40～60 人天（置信度中，附相似历史需求 2 条）；IT 决策 5 项，每项 2～3 个选项 + 推荐 + ADR 记录 |

对账场景（贯穿）：运营三天后又说"客户版不用风险指标了，但要加同类产品对比"——「需知」自动比对两版：删了什么、加了什么、工时从 5 变 7 人天、新增 2 条要确认（同类怎么定义、对比口径）。

## 2. 产品与技能

延续研伴的包装做法：一个有名字的"人" + 两字技能 + 一道安全门。

**候选名字**（Jerry 定）
1. **「需知」**（推荐）—— 谐音"须知"，意思是"需求先知 / 开工须知"；技能可全部用"知"或"清"的意象。
2. 「译需」—— 直白，"需求翻译官"的两字版。
3. 「先问」—— 强调方法论："先问清，再开工"。

**技能（以「需知」为例）**

| 技能 | 做什么 | 输入 | 输出 |
|---|---|---|---|
| **问清** | 从乱七八糟的输入抽取目标、角色、触发、输入输出、频率、时效、数据来源、非功能项，识别隐含假设；生成**待确认清单**（影响大 / 中 / 可默认三档，每条附默认假设和"不问会怎样"）；一键生成给业务的确认消息 | 聊天记录 / 纪要 / 邮件 / 语音转写 / Word | 需求卡片 + 待确认清单 + 确认消息 |
| **写单** | 生成**双版需求单**：业务版一页纸（业务能签字）+ 技术版（用户故事、Given/When/Then 验收标准、数据字典、接口草案、非功能）；每条技术条目回链到业务原话 | 需求卡片 + 业务答复 | 业务版 / 技术版 需求单 |
| **估量** | 六维复杂度（功能点 / 数据接入 / 界面 / 权限 / 性能 / 合规）→ 工时区间（乐观 / 中位 / 悲观）+ 依据；**类比估算**：检索历史需求库找相似需求，用实际工时校准，给置信度 | 需求单 + 历史需求库 | 复杂度雷达、工时区间、相似需求、置信度 |
| **定架** | 技术栈 / 架构建议 + **IT 决策清单**（新建 vs 复用、数据来源、批 vs 实时、权限模型、部署位置、是否走 AI 平台），每项 2～3 个选项 + 推荐 + 理由 + 影响，生成 ADR；**复用发现**：对照公司系统 / 组件目录指出"已有 X 覆盖 60%" | 需求单 + 系统目录 | 架构草图、决策清单、ADR、复用建议 |
| **出样** | 生成可点击的 HTML 原型（页面、按钮、表格、假数据）给业务确认——"看得见的需求" | 需求单 | 原型页 |
| **对账** | 需求版本管理：新版本一进来自动 diff——增删改了什么、工时与架构影响、要重新确认什么；任务拆分与里程碑同步更新；上线后实际工时回写 | 新版本输入 | 变更影响报告、任务清单更新 |
| **隐盾**（复用研伴） | 输入进模型前脱敏：客户字段、账号、内网地址、密钥 | 任何文本 | 脱敏文本 + 日志 |

## 3. 六个亮点（创新分从这里拿）

1. **问的是期货问题，不是软件问题**：内置"期货 IT 需求追问知识库"（夜盘与结算时点、交易日历、主力合约切换、合约换月与交割月、涨跌停与保证金调整、品种单位与精度、口径（复权 / 结算价 / 收盘价）、权限与脱敏、监管报送口径……），通用工具（spec-kit 的 clarify、BMAD 的 analyst）问不出这些。**可作个人赛知识库赛道作品**。
2. **不拍脑袋的工时**：类比估算 + 置信度 + 上线后实际工时回写 → 越用越准的估算飞轮（方案里给出"估算偏差从 x% 降到 y%"的口径）。
3. **告诉领导要拍板什么**：IT 决策清单 + 每项选项 / 推荐 / 影响 + ADR 自动归档——把"架构评审"前置到需求阶段。
4. **复用发现，少建重复系统**：对照系统 / 组件目录（Demo 用虚构目录 10 个系统）指出能复用什么；对"可复制推广"维度也有说服力（每个子公司的目录不同，换目录即可）。
5. **业务看得懂、开发能直接干**：双版需求单 + 可点原型；现场演示"业务改一句话，原型跟着变"。
6. **改了什么一眼看**：需求变更对账——增删改、工时影响、需重新确认项；解决"需求改来改去没人记"的老问题。

（第 7 个可选亮点：**纪要直通车**——晨会 / 周会纪要贴进来，自动识别哪几段是需求、各自起一张卡片。Jerry 本来就写纪要，演示很自然。）

## 4. Demo 设计（现场可跑、全虚构）

**载体**：Streamlit 网页，沿用研伴技术栈（`llm.py` / `config.py` / `.env` OpenAI 兼容接入、`privacy.py` 隐盾、SQLite 台账、mock 模式无 key 可跑、品牌化界面）。

**页面**：收需求（粘贴 / 上传 / 选样例）→ 问清（清单 + 确认消息 + 模拟业务回答后重算）→ 需求单（业务版 / 技术版切换）→ 估量（六维雷达 + 区间 + 相似历史需求）→ 定架（架构图 + 决策清单 + 复用发现）→ 出样（内嵌原型页）→ 对账（版本 diff）→ 台账（全部需求、飞轮统计：澄清轮次、估算偏差）。

**虚构数据**：4 个样例需求（§1）；历史需求库 30 条（含实际工时）；公司系统 / 组件目录 10 个（报表平台、交易系统、行情服务、风控系统、消息推送、OA、数据仓库、AI 平台、权限中心、文件服务）；期货追问知识库 60 条规则；评测集 30 条需求（每条配专家版待确认清单与工时）。

**现场 3 分钟**：贴样例 ①（微信原话）→ 30 秒出待确认清单与确认消息 → 点"业务已答复"（预置答复）→ 双版需求单 + 工时区间 + 决策清单 + 复用发现 → 打开原型页 → 贴一段"改需求"看对账 → 台账页看飞轮 → **现场让评委口述一个需求（附加分：真实交互）**。

**评测指标（方案文档要有数）**：待确认问题覆盖率（对专家清单）、问题精准率（无废问）、工时估算误差（对历史实际）、需求单完整性评分（模板项覆盖）、变更 diff 准确率、脱敏漏检率。`eval_req.py` 跑分。

## 7. 安全合规

- 需求文本可能夹带客户名、账号、内网地址 → 隐盾先脱敏，模型只见脱敏文本；本地规则兜底。
- 不接生产数据库、不读代码仓库（复用发现只看系统目录元数据）。
- 全程留痕：谁提、AI 说了什么、业务怎么答、最终怎么定、实际工时多少 —— 满足内部审计，也是飞轮数据。
- 模型走公司 AI 平台 API（OpenAI 兼容），不出公网。

## 8. 赛别、组队与个人赛拆分

- **团队赛**：主报研伴还是「需知」，等组队情况定（研伴需要投研同事多；「需知」天然是"技术部 3 人 + 业务方 1～2 人"，业务同事在队里就是用户，跨部门附加分好拿）。
- **个人赛**（可同报，最终只得一项）：技能赛道 —— "问清"提示词（角色 / 约束 / 输出规范 / 追问规则引用）；工具赛道 —— 原型生成或工时估算小工具；知识库赛道 —— 期货 IT 需求追问知识库（自备 ≥10 道问题）；金点子赛道 —— 整体构想与立项路径。与研伴的四件个人赛作品不重叠。
